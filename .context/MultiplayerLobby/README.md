# 멀티플레이 로비 작업 안내

> 상태: 활성
> 역할: 이 작업의 진입점과 문서 라우팅
> 마지막 구조 갱신: 2026-10-15

## 1. 목적

이 폴더는 패키지 빌드에서 실제 멀티플레이를 하기 위한 프론트엔드·접속·대기실·세션 흐름을 하나의 작업 단위로 관리한다.

핵심 목표는 다음과 같다.

- 게임을 처음 실행하면 메인 메뉴에서 **호스트(방 생성)** 또는 **게스트(기존 방 참가)**를 고른다.
- 여러 명이 대기실에 모여 함께 시작하거나, 이미 진행 중인 게임에 **중간 참가**한다.
- 접속 실패·호스트 종료·정원 초과 같은 비정상 경로에서 메인 메뉴로 안전하게 돌아온다.
- IP 직접 접속으로 시작하고, 세션 계층(LAN 방 목록)을 거쳐 온라인 백엔드(Steam 또는 EOS)를 붙일 수 있게 한다.

범위 밖: 데디케이티드 서버(별도 작업, 이 작업은 맞물리는 경계만 지킨다 — L-008), 화면 분할, 게임 종료 후 로비 복귀(승리 조건·세션 관리가 정해진 뒤 Phase 추가). 상세는 `Roadmap.md` §5.

## 2. 세션 시작 시 필수 문서

1. `README.md`
2. `Current.md`
3. `Decisions.md`

이 세 문서를 읽은 뒤 현재 작업에 필요한 문서만 아래 라우팅 표에 따라 추가로 읽는다. `history/`와 현재 단계보다 먼 `phases/` 문서는 기본 컨텍스트에 올리지 않는다.

## 4. 아키텍처 한 장 요약

`L_Frontend`(메인 메뉴, 월드 생성 없음)
→ 호스트: 게임 맵을 `?listen`으로 연다(Phase 3부터는 `L_Lobby?listen`)
→ 게스트: 주소로 접속한다(Phase 4부터는 세션 계층이 주소를 찾아 준다)
→ 게임 맵: 기존 4단계 초기화와 투-게이트가 호스트·즉시 참가·중간 참가를 모두 처리한다
→ 실패·종료: `ULNPGameInstance`가 네트워크·트래블 실패를 받아 `L_Frontend`로 돌려보내고 사유를 띄운다

상세는 `design/Architecture.md`가 소유한다.

## 5. 핵심 용어

| 용어 | 의미 |
|:---|:---|
| 호스트 | 리슨 서버를 여는 플레이어. 방 = 호스트의 리슨 서버 월드 |
| 게스트 | 호스트에 접속하는 클라이언트 |
| 프론트엔드 | 실행 직후의 메인 메뉴 맵 `L_Frontend`. 네트워크 연결이 없는 Standalone 월드 |
| 대기실(로비) | 게임 시작 전 참가자가 모이는 경량 맵 `L_Lobby`. 메뉴 UI만 있고 옥탄트를 생성하지 않는다(L-005) |
| 즉시 참가 | 게스트가 호스트 서버 초기화가 끝나기 전에 접속하는 경우 |
| 중간 참가 | 게스트가 서버 초기화 완료(`ServerPhase == Complete`) 뒤 접속하는 경우 |
| 접속 진입점 | GameInstance의 "주소로 접속" 단일 함수. 세션 계층·온라인 백엔드가 이 앞에 끼어든다 |
| 세션 계층 | 방 생성·검색·참가를 백엔드(LAN·Steam·EOS)에서 추상화한 층. Phase 4 도입 |

## 6. 모든 구현이 지켜야 하는 불변 조건

- 리슨 서버 월드는 맵 로드 시점부터 listen이다. 실행 중인 Standalone 월드를 Listen으로 바꾸지 않는다(L-002).
- 맵 전환은 non-seamless다(L-003).
- 옥탄트 생성·SurfaceData·Mass 스폰은 게임 맵에서만 일어난다. 프론트엔드·대기실 맵은 이를 일으키지 않는다(L-005).
- 중간 참가는 기존 투-게이트 초기화를 그대로 쓴다. 로비·메뉴 전용 late-join 경로를 만들지 않는다(L-006).
- 명령줄로 맵 URL을 받은 실행(회귀·성능 하네스)은 메뉴를 거치지 않고 지금처럼 동작한다(L-007).
- 메뉴·대기실은 접속 진입점 하나로만 접속한다. 백엔드별 접속 코드를 위젯에 두지 않는다.
- 모든 비정상 종료 경로는 메인 메뉴로 돌아오고 사유를 보여 준다. 게임이 멈추거나 빈 월드에 남지 않는다.
- 정원은 서버 모드별 설정이다. "호스트 = 로컬 플레이어" 가정은 리슨 전용 분기에만 둔다(L-008).

## 7. 문서별 소유 정보

- `README.md`: 작업 범위, 불변 조건, 문서 라우팅
- `Current.md`: 지금의 상태와 바로 다음 행동
- `Decisions.md`: 모든 세션이 알아야 하는 확정 결정
- `Roadmap.md`: 단계 순서와 Phase 게이트
- `design/`: 현재 유효한 상세 기술 설계와 검증 규약
- `research/`: 엔진·플랫폼 조사, 실험 결과, 미확정 근거
- `phases/`: 해당 단계의 실행 계획과 완료 조건
- `history/`: 이미 끝난 작업, 측정 기록, 시행착오

정보의 원본은 한 곳에만 둔다. 다른 문서에서는 요약과 링크만 제공한다.

## 8. 문서 갱신 규칙

### 세션 시작

1. 필수 문서 세 개를 읽는다.
2. `Current.md`의 현재 Phase와 다음 행동을 확인한다.
3. 라우팅 표에서 필요한 설계·조사·Phase 문서만 읽는다.
4. 코드와 에셋의 실제 상태가 문서와 일치하는지 확인한다.

### 작업 중

- 새 영구 규약은 해당 `design/` 문서에 반영한다.
- 이 작업 전체가 지켜야 하는 결정이면 `Decisions.md`에도 한 줄을 추가한다.
- 실험 수치와 조사 근거는 `research/` 또는 현재 Phase 로그에 기록한다.

### 세션 종료

1. `Current.md`를 실제 상태로 갱신한다.
2. 수행 내용과 검증 결과를 현재 `history/PhaseNN_Log.md`에 날짜별로 추가한다(없으면 만든다).
3. 완료 조건을 충족하면 Phase 문서 체크리스트를 갱신한다.
4. 설계가 바뀌었다면 관련 `design/`과 `Decisions.md`를 먼저 고친다.
5. 다음 세션이 바로 실행할 수 있는 구체적인 한두 작업을 남긴다.

### Phase 종료

1. 해당 Phase 완료 조건과 테스트 증거를 로그에 남긴다.
2. `Roadmap.md`의 상태를 갱신한다.
3. `Current.md`를 다음 Phase 기준으로 짧게 다시 작성한다.
4. 다음 Phase 실행 문서는 착수 직전에 생성하거나 구체화한다.
5. 구현으로 바뀐 프로젝트 공통 설계(`TechDesign_InitSequence.md`, `TechDesign_InGameMenu.md` 등)를 갱신한다.

## 9. 문서 상태 표기

| 상태 | 의미 |
|:---|:---|
| 활성 | 매 세션의 현재 진입점 |
| 확정 | 변경 전 명시적 재논의가 필요한 결정 |
| 기준 설계 | 구현이 따라야 하는 현재 기술 설계 |
| 초안 | 구현·스파이크 결과에 따라 바뀔 수 있음 |
| 검증 필요 | 엔진 또는 프로젝트 실험이 남아 있음 |
| 완료 | 해당 Phase의 완료 조건과 검증을 통과 |
| 보관 | 최신 설계가 아니며 역사 추적용 |
| 폐기 | 사용하지 않으며 기각 이유만 보존 |

## 10. 컨텍스트 예산 원칙

- 필수 세 문서는 합계 약 4,000~6,000토큰 이하를 목표로 한다.
- `Current.md`는 완료 이력을 누적하지 않고 200줄 이하를 유지한다.
- `Decisions.md`는 결론 중심의 표로 유지하고 상세 근거를 링크한다.
- 먼 미래 Phase는 `Roadmap.md`의 요약만 유지하며 착수 전에 상세화한다.
- 히스토리는 기본 로딩하지 않고 `rg` 검색으로 관련 날짜·키워드만 찾는다.

## 11. 현재 진입점

현재 작업 위치와 다음 행동은 `Current.md`를 따른다. 전체 순서를 다시 조정해야 할 때만 `Roadmap.md`를 읽는다.
