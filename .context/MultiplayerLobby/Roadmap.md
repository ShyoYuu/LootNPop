# 멀티플레이 로비 로드맵

> 상태: 기준 로드맵
> 읽기 조건: Phase 전환, 전체 순서 변경, 작업 범위 재산정 시
> 마지막 갱신: 2026-10-15

## 1. 진행 원칙

- 한 번에 모든 기능을 만들지 않는다. 각 Phase는 패키지 빌드에서 그 자체로 플레이 가능한 상태로 끝난다.
- 각 Phase는 독립적으로 검증하고 커밋할 수 있어야 한다.
- 백엔드에 의존하지 않는 흐름(메뉴·접속·초기화·실패 복귀·대기실)을 먼저 완성하고, 백엔드는 마지막에 붙인다(L-001).
- 미래 Phase의 상세 실행서는 착수 직전에 작성한다.
- 모든 Phase 완료 조건에 다음 두 가지를 포함한다.
  - `design/Validation.md` §4 공통 스모크(패키지 빌드, 같은 PC 다중 인스턴스)
  - 기존 명령줄 리슨 2P 하네스 회귀(L-007)

## 2. 단계 의존성

`Phase 1 프론트엔드와 IP 직접 접속`
→ `Phase 2 5인과 중간 참가 강건화`
→ `Phase 3 메뉴 UI 대기실`
→ `Phase 4 세션 계층과 LAN 방 목록`
→ `Phase 5 온라인 백엔드`

Phase 2와 3은 서로 독립적이라 순서를 바꿀 수 있다(사용자 판단). Phase 4는 Phase 3의 대기실 상태(진행 중 여부·인원)를 세션 속성으로 광고하므로 3 뒤에 둔다.

## 4. Phase별 범위 보충

### Phase 1

사용자가 예로 든 첫 단계다. 대기실 없이 호스트가 메뉴에서 곧바로 게임 맵을 listen으로 열고, 게스트는 IP를 입력해 진행 중인 게임에 들어간다. 중간 참가는 이미 동작하므로(L-006) 이 Phase의 위험은 "메뉴에서 시작하는 경로"와 "실패 시 돌아오는 경로"다. 상세는 Phase 문서가 소유한다.

### Phase 2

- 정원: GameSession `MaxPlayers` 5, 초과 시 PreLogin 거부 사유를 게스트 메뉴에 표시(L-004). 값은 서버 모드별 설정에서 읽고 코드에 5를 박지 않는다(L-008 ①). 이탈 정리·입장 알림도 "나간 사람이 호스트인가"를 리슨 전용 분기로 둔다(L-008 ②).
- 스폰 지점: TestMap03 PlayerStart가 4개뿐이고 `ChoosePlayerStart`가 기본 추첨이다. 5개 이상과 점유 회피가 필요하다.
- 플레이어 이름: 메뉴 입력 → 접속 URL 옵션 → PlayerState. HUD·대기실에서 쓴다.
- 입장/퇴장 알림, 참가자 목록(인게임 메뉴 또는 HUD 최소 표시).
- 이탈 정리: 나간 플레이어의 폰·인벤토리·LootDice(사망 시 전량 드랍 규칙과의 관계), 적 슬롯 타겟팅, 락온, 협동 루팅 진행 중 이탈. 현재 `Logout` 오버라이드가 없다.
- 버전 불일치 거부: 다른 빌드끼리 접속하면 사유와 함께 거부한다.
- 측정: 리슨 5P에서 호스트 frame P95와 업로드. 클라이언트당 대역폭 상한 150KB/s × 게스트 4명이 호스트 업로드 상한이다. 적 타깃 후보 `PotentialTargets[4]`, 플레이어별 Actor 승격 슬롯처럼 인원에 비례하거나 4인을 전제한 부분을 함께 본다.

### Phase 3

- 호스트 시작이 `L_Lobby?listen`으로 바뀐다. 게스트는 대기실로 들어온다.
- 대기실 GameState가 참가자 목록·준비 상태를 복제하고, 호스트가 시작하면 non-seamless 서버 트래블로 게임 맵을 연다(L-003). 게임 맵의 4단계 초기화가 모든 게스트에게 즉시 참가 경로로 돈다.
- 게임이 진행 중인 방에 새로 접속한 게스트는 서버가 이미 게임 맵에 있으므로 중간 참가 경로를 탄다(L-006).
- 결정할 것: Phase 1의 "바로 시작" 경로 유지 여부, 시드·편성 같은 게임 옵션을 대기실에서 고를지.
- 시작 조건은 교체 가능한 규칙으로 둔다. 리슨은 "호스트가 시작"이고, 데디서버는 호스트가 없으므로 인원 충족·전원 준비·투표 같은 다른 규칙을 끼울 수 있어야 한다(L-008 ②). 이 Phase에서는 리슨 규칙만 구현한다.
- 확인할 위험: 서버 트래블 시 Mass·Iris·월드 서브시스템 정리(현재 맵 재로드·라운드 재시작은 미구현, [TechDesign_InitSequence.md](../TechDesign_InitSequence.md) §6).

### Phase 4

- 메뉴·대기실은 계속 접속 진입점 하나만 부르고, 세션 계층이 그 앞에서 주소를 찾아 준다.
- LAN 세션(Null 백엔드)으로 방 생성·검색·참가와 세션 속성 갱신(인원·진행 중)을 만든다. IP 직접 입력은 남긴다.
- OSS v1 / Online Services / CommonUser 중 무엇을 쓸지는 착수 시 조사로 정한다(`research/OnlineBackends.md` §4).
- 세션 속성·검색 결과 형식은 리슨 방과 데디서버를 구분할 수 있게 둔다(서버 종류·정원). 데디서버 광고는 구현하지 않는다(L-008 ③).

### Phase 5

- 착수 전 결정 게이트: Steam / EOS / 보류. 판단 근거는 `research/OnlineBackends.md`.
- 첫 단위는 반드시 NetDriver 스파이크다. 선택한 백엔드의 NetDriver에서 Iris·MassReplication 복제, 패키지 리슨 2P와 중간 참가가 동작하는지 먼저 확인한다.
- 선택 기준에 데디서버 지원(서버 광고·검색, 플레이어 없는 서버 로그인)을 포함한다(L-008 ③).

## 5. 범위 밖과 후속 작업

### 데디케이티드 서버(별도 작업, L-008)

리슨 서버보다 큰 정원을 받는 데디서버는 가장 후순위로 개발할 예정이며, 이 폴더가 아닌 별도 작업 폴더로 진행한다. 시작은 이 작업의 Phase 4 이후다. 분리하는 이유는 작업의 대부분이 로비와 무관하기 때문이다.

- **빌드 인프라**: `LootNPop.uproject`의 `EngineAssociation`이 `"5.8"`(런처 설치 엔진)이다. Server 타깃은 소스 빌드 엔진이 필요하고, 현재 타깃은 Game·Editor 둘뿐이다. 엔진 전환, 서버 타깃, 쿡·배포 파이프라인이 필요하다.
- **로컬 플레이어 없는 서버 점검**: 테스트 외 소스의 `GetFirstPlayerController` 계열 호출 15곳, 렌더링 없는 서버의 Mass 표현 프로세서·애니메이션·VFX. `NM_DedicatedServer`를 다루는 파일은 2개뿐이다(2026-10-15 기준).
- **인원 확장 성능**: 플레이어가 늘면 깨어 있는 Pod가 늘어 활성 적이 증가한다(`SurfaceSupportNavigation` D-076, 동시 활성 상한 약 2,000). 서버 업로드는 클라이언트 수 × 150KB/s, 적 타깃 후보는 `PotentialTargets[4]`다.

이 폴더에서 다시 쓰는 것: 서버 목록 검색·접속 진입점·실패 복귀·중간 참가. 로비 작업은 L-008의 경계만 지키고, 데디서버 접속을 메뉴에 붙이는 일은 데디서버 작업이 이 폴더의 세션 계층을 사용해 진행한다.

### 그 밖의 범위 밖

- 게임 종료 후 로비 복귀: 승리 조건·세션 관리(`DevelopmentPlan.md`)가 정해지면 Phase를 추가한다.
- 화면 분할.
