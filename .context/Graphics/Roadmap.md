# 그래픽스 작업 로드맵

> 상태: 기준 로드맵
> 읽기 조건: Phase 전환, 전체 순서 변경, 범위 재산정, JustDodge 이관 항목 확인 시
> 마지막 갱신: 2026-11-07

## 1. 진행 원칙

- **측정이 먼저다(GX-003).** 최적화와 렌더 패스의 비용은 Phase 0의 측정 하네스로 잰다. 수치가 없는 "최적화"는 완료로 치지 않는다.
- **콘텐츠는 벤치마크 씬 범위만 채운다(GX-004).** 아트 품질을 올리는 것이 목표가 아니라, 측정 결론이 실제 게임에서도 통하게 하는 것이 목표다.
- 각 Phase는 따로 검증하고 커밋할 수 있어야 한다.
- 다음 Phase의 상세 실행서는 착수 직전에 쓴다.
- 모든 Phase의 완료 조건에 다음 세 가지를 넣는다.
  - 측정 결과(전후 수치, `design/Measurement.md` 보고 형식)
  - 포트폴리오 산출물(README §6)
  - 깨끗한 트리에서 Build.bat 통과

## 2. 단계 의존성

`Phase 0 측정 하네스·기준선`
→ `Phase 1 벤치마크 콘텐츠`
→ `Phase 2 군중 렌더링 분석·최적화`
→ `Phase 3 커스텀 렌더 패스`
→ `Phase 4 구면 지형 흔적`

- Phase 3은 콘텐츠와 무관한 풀스크린 패스가 많아 기술적으로는 Phase 1·2와 병행할 수 있다. 하지만 사용자 결정(GX-003)에 따라 순서대로 한다.
- 단위 N(Niagara 원거리 정밀도 조사)은 Phase 0 직후에 한다(GX-009). JustDodge V3b(월드 스페이스 이동 꼬리)의 게이트다.
- JustDodge 비주얼 1차(V1a·V2·V3a·V4a)는 그래픽스와 무관해서 Phase 0보다 먼저 진행된다(J-020). 이 작업의 순서(GX-003)는 바뀌지 않는다.
- Phase 3-3(캐릭터 강조 채널)은 Phase 2에서 확정한 적 표현 구성(ISKM·ISM·VAT) 위에서 설계한다.

## 4. Phase별 범위 보충

### Phase 0 — 측정 하네스와 기준선

지금의 마네킹·저품질 NPC 상태에서도 개수·구조에 비례하는 비용(인스턴스 수, 드로우콜, 그림자 캐스터 수, 렌더 스레드 비용)은 의미가 있다. 콘텐츠를 넣은 뒤와 비교할 출발점으로 기준선을 먼저 찍는다.

- 패키지 빌드 측정 절차를 만든다(구성, 실행 인자, 산출물 경로).
- 재현 가능한 카메라 경로를 만든다. 레벨 시퀀스로 할지 스크립트 관전 경로로 할지는 실행서에서 정한다.
- 측정 편성 에셋을 만든다. 초기 1k / 3k / 5k 초안은 사용자 선택(2026-11-07)에 따라 기존 스폰을 유지한 Low / Medium / High와 실제 생성 수 표기로 구체화했다. 세부 값은 [Phase 0 실행서](phases/Phase00_MeasurementBaseline.md)를 따른다. 기본 편성은 건드리지 않는다.
- 도구별 용도를 정한다(`design/Measurement.md` §4).
- 내부 해상도와 업스케일러를 정한다(GX-002 세부).
- 산출물: 기준선 보고서.

### Phase 1 — 벤치마크 콘텐츠 (트랙 C)

- **옥탄트 1개를 고밀도로 꾸민다.**
  - ElectricDreamsEnv·Project Titan의 스태틱 메시와 머티리얼만 쓴다. 두 샘플은 평면 Landscape 기반이라 지형 자체는 구면에 쓸 수 없다.
  - 배치는 PCG로 하고 Nanite를 켠다. 옥탄트 형상 소유권과 이음매 규약을 따른다([Guide_OctantLevelInstance.md](../Guide_OctantLevelInstance.md)).
- **파라곤 적 2~3종을 만든다.**
  - IK Retargeter로 기존 적 애니메이션을 옮긴다. 리타깃 함정은 AnimationOverhaul 기록을 따른다.
  - ISKM 요건([TechDesign_EnemyNPC_LowLOD.md](../TechDesign_EnemyNPC_LowLOD.md) §6.7)을 지킨다: 전 LOD `bOptimizeForInstancing`, 머티리얼 usage 플래그, 제자리 클립, additive 클립 금지.
  - 무기는 지금처럼 별도 스킨드 메시로 둔다.
  - 파라곤 캐릭터는 폴리곤과 머티리얼 슬롯이 많다. 반입한 원본 상태를 그대로 측정해 두면 Phase 2의 최적화 출발점이 된다.
- **라이선스:** 에셋은 git에서 제외하고 재생성 절차만 남긴다(GX-004). 정확한 재배포 조건은 착수 시 Fab 라이선스 문구로 확인한다.
- **시간 상한:** 세션 4개를 넘기면 범위를 줄인다.
- 산출물: Phase 0 측정을 다시 돌려 콘텐츠가 비용 구조를 어떻게 바꿨는지 보고한다(예: CPU 병목에서 GPU 병목으로 이동했는지).

### Phase 2 — 대규모 적 전투 렌더링 비용 분석과 최적화 (트랙 P)

| 단위 | 내용 |
|:---|:---|
| 2-1 비용 곡선 | 적 수 × 화면 점유율 × 캐릭터 종류에 따라 Game Thread / Render Thread / GPU 비용이 어떻게 변하는지 측정한다 |
| 2-2 슬롯 분리 | 몸통·무기·머티리얼 슬롯 분리가 인스턴스 배치와 드로우 수에 주는 영향을 확인한다. 머티리얼 통합·섹션 병합 전후를 비교한다 |
| 2-3 요인별 절제 | 메시 LOD, 애니메이션 표현, 그림자, 머티리얼 복잡도를 하나씩 바꿔 효과를 비교한다. 절제 측정 규약은 [Guide_NetBandwidth.md](../Guide_NetBandwidth.md)를 재사용한다 |
| 2-4 VAT 대안 (게이트) | 2-1~2-3 결과가 ISKM의 한계를 보일 때만 진행한다. Vertex Animation Texture 베이크 파이프라인과 인스턴스별 커스텀 데이터 재생을 만들어 ISKM과 비교한다 |
| 2-5 전환 팝핑 | ISKM↔ISM↔Actor 전환에서 포즈 튐과 화면상 팝핑을 줄인다(GX-005) |

- 2-3 그림자 가설: 애니메이션되는 비-Nanite 인스턴스가 Virtual Shadow Map 캐시 페이지를 매 프레임 무효화한다. 측정으로 확인한다.
- 2-5 후보:
  - ISKM↔ISM: 디더 크로스페이드, 거리 히스테리시스, ISM 정지 포즈를 현재 시퀀스와 비슷한 프레임으로 맞추기
  - ISKM↔Actor: 승격 순간의 시퀀스 위상을 Actor 첫 포즈에 정합하기, 또는 1~2프레임 이중 표시와 디더
  - Motion Matching과 시퀀스 위상 동기화가 근본적으로 맞지 않는다는 §6.6의 근거를 먼저 다시 확인한다.
- 측정 항목에 JustDodge 잔상(V2) 반투명 비용을 등록한다. V2는 JustDodge 비주얼 1차에서 이 Phase보다 먼저 구현된다(J-020).
- 산출물: 비용 곡선 그래프, 절제 표, 목표 예산(GX-002) 안에 드는 표현 구성 권고.

### Phase 3 — 커스텀 렌더 패스 (트랙 R)

| 단위 | 내용 |
|:---|:---|
| 3-1 렌더 모듈 기반 | 셰이더 디렉터리 매핑, `FSceneViewExtensionBase`, RDG 패스 1개(디버그 틴트). 프로젝트의 첫 `.usf`가 된다. 렌더러·RDG 분석 문서(`EngineAnalysis_RDG.md`)를 함께 쓴다 |
| 3-2 화면 효과 레이어 | 효과 요청 인터페이스, 우선순위·블렌드 가중치. 첫 소비자는 JustDodge 로컬 화면 연출(채도 감소·색수차·방사형 블러, JustDodge V5에서 트리거 연결). 피격·저체력 슬롯을 예약한다 |
| 3-3 캐릭터 강조 채널 | CustomDepth/스텐실과 오버레이 중 하나를 고른다. 소비자: 스캔 강조, JustDodge 버프 림라이트·나타남 플래시(JustDodge V6) |
| 3-4 스캔 시야 | 구면을 따라 퍼지는 파동, 통과한 적·LootPod 일정 시간 강조, 보이는 부분과 가려진 부분의 다른 표시 |
| 3-5 (선택) 반경 높이 안개 | 행성 중심 기준 높이로 안개 밀도를 계산하는 패스 |

- **3-3 검증 필요:** 적 대부분이 PureEntity라 ISKM·ISM 컴포넌트 하나가 여러 인스턴스를 그린다. CustomDepth·스텐실은 컴포넌트 단위 설정이므로 인스턴스별 강조가 불가능할 수 있다. 대안은 인스턴스별 커스텀 데이터로 머티리얼에서 강조하는 것이다. 엔진 동작을 먼저 확인한다.
- **3-4 설계 초안:**
  - 파면은 평면 거리가 아니라 **행성 중심 기준 각도(측지 거리)**로 계산한다. 픽셀 위치는 SceneDepth에서 월드 위치를 복원해 얻는다.
  - 파면이 지나간 시각을 대상별로 기록해 일정 시간 강조한다. 대상 수집은 [TechDesign_TargetQuery.md](../TechDesign_TargetQuery.md)의 공간 분할을 재사용한다.
  - 보이는 부분과 가려진 부분은 CustomDepth와 SceneDepth를 비교해 다르게 그린다(가려진 부분은 엑스레이 실루엣).
  - LootPod Low LOD 빛기둥과 겹칠 때의 관계를 정한다.
  - 미결(기획): 협동 플레이에서 스캔 결과를 공유할지, 발동 수단(GA·쿨다운·입력)을 어떻게 할지. 착수 전에 사용자와 정한다.
- **3-5 배경:** 엔진 `ExponentialHeightFog`는 월드 Z 높이를 가정한다. 반면 SkyAtmosphere와 볼류메트릭 클라우드는 행성 중심을 지원한다. 이 경계를 분석한 결과를 함께 남긴다.

### Phase 4 — 구면 지형 흔적 (트랙 S)

화염방사기(그을림), 런처(폭발 자국), 라이플(탄흔)이 지형에 남기는 흔적을 만든다.

| 후보 | 방식 | 맞는 흔적 |
|:---|:---|:---|
| (a) DBuffer 데칼 풀 | 착탄 지점 법선 방향 투영. 개수와 수명에 상한을 둔다 | 라이플 탄흔, 런처 폭발 자국 |
| (b) 구면 파라미터화 누적 텍스처 | 큐브 스피어 렌더 타깃에 그을림을 누적하고(렌더 타깃 또는 컴퓨트), 지형 머티리얼이 행성 중심 방향으로 샘플링한다 | 넓게 쌓이는 화염 그을림 |

- RVT는 박스 볼륨의 Z 축 투영이라 구면에 맞는지 검증해야 한다.
- 착수할 때 스파이크로 방식을 정한다. 두 방식을 섞을 수도 있다.
- 트리거는 기존 착탄·폭발·화염 큐에서 받는다(GX-007). 판정 경로는 [TechDesign_HitDetection.md](../TechDesign_HitDetection.md)를 따른다.
- 지형 머티리얼을 고쳐야 하면 옥탄트 형상·머티리얼 소유권을 먼저 확인한다.

JustDodge 비주얼 트랙은 이 표의 게이트를 기준으로 나뉜다(J-020). 그래픽스와 무관한 1차(V1a·V2·V3a·V4a)는 Phase 0보다 먼저 진행된다. 1차는 로컬 스페이스 Niagara만 쓰고 캐릭터 오버레이 머티리얼을 쓰지 않으므로, 이 작업의 3-3 설계를 제약하지 않는다. 2차(V3b·V5·V6)는 위 표의 받는 단위(N·3-2·3-3)가 끝난 뒤에 진행된다.

## 6. 범위 밖과 후속 후보

- 윈드필드 GPU 연동: 게임플레이 윈드필드를 컴퓨트로 변위 텍스처에 써서 풀·Niagara가 샘플링한다. 구면 파라미터화는 Phase 4 (b)와 공유할 수 있다.
- 행성 지평선과 원거리 표현: 곡률이 드러나는 원거리 옥탄트의 LOD·HLOD·지평선 너머 컬링.
- 엔진을 수정해야 하는 셰이딩 모델 추가(GX-008).
