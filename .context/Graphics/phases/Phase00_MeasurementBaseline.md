## 1. 시작 조건과 이번 작업의 경계

- JustDodge 비주얼 1차는 [Current.md](../../JustDodge/Current.md) 기준 주요 검증을 마감했다. 기존 미검증 항목을 통과한 것으로 확대하지 않는다.
- V2 잔상 비용 측정은 Phase 2가 소유한다. 이번 기준선에서는 저스트 회피를 발동하지 않는다.
- 기존 메시·머티리얼·렌더 설정을 기준으로 측정한다. 콘텐츠 반입과 최적화는 다음 Phase다.
- Phase 0에는 고밀도 아트 구성이 필요하지 않다. 사용자는 2026-11-06 Meadow 테스트 맵을 제외하고 Acropolis 프로토타입을 선택했다. 고밀도 콘텐츠 투입 전후 비교는 Phase 1에서 한다.
- 각 구현 단위가 끝나면 결과를 보고하고 사용자의 계속 진행 확인을 받는다.
- 수동 PIE·GUI 조작이 더 빠르거나 화면의 적절성을 판단해야 하면 자동화 구현 전에 요청한다.

### 경로와 장면을 고정하는 방법

- 구역 추천 근거는 공간 설계 문서다. Acropolis는 열린 지상·부유섬을 첫 군중 기준선에 활용하기 좋고, Bastion은 성벽·성채의 가림과 다수 광원, Pyramid는 복층 실내의 가림을 포함한 시나리오에 적합하다. 이는 측정 전 판단이며 성능 순위가 아니다. 하나만 선택하고 다른 두 구역의 추가 측정은 이번 필수 범위에 넣지 않는다.
- 카메라 위치·회전·FOV, 구간별 시간과 보간 방식을 저장한다. 월드 Z를 Up으로 가정하지 않는다.
- 근거리 군중, 중거리 군중, 원거리와 구면 곡률이 보이는 구간을 넣는다. 실제 가시 개체 수·표현 분포를 함께 기록한다.
- 카메라와 플레이어 위치 중 무엇을 LOD·유의도·AI가 참조하는지 먼저 확인한다. 카메라만 움직이는 구성이 의도한 부하를 만들지 않으면 경로 방식을 다시 제안한다.
- Phase 0의 첫 시나리오는 입력 없이 관찰한다. AI·애니메이션은 유지하고, 전투 유무와 플레이어 생존·개체 수 변화는 기록한다. 이를 전투 부하 측정으로 표현하지 않는다.
- 고정 시드는 초기 배치의 재현 조건이다. AI·물리·애니메이션의 프레임 단위 결정론을 보장한다고 쓰지 않는다.

## 3. 코드에서 확인한 제약

2026-11-06 착수 전 읽기 확인 결과다. 이후 에셋·패키지 검증 결과는 아래 단위별 체크리스트와 로그를 따른다.

- `LNPMassSpawnSubsystem.cpp`: `LNP.Spawn.ConfigOverride`와 패키지용 `-LNPSpawnConfig=<object path>`가 이미 있다. 오버라이드 로드 실패 시 기본 편성으로 폴백하지 않는다.
- `LNPMassSpawnConfig.h`: 편성은 Pod 세트 수와 연결 적 수로 구성된다. 기본 에셋을 복제해 별도로 작성한다.
- `LNPMassSpawnPlan.cpp`: 베이크 후보·간격·머리 위 공간 제약으로 요청 수보다 적게 놓일 수 있다. authored 앵커의 적 편성은 에셋의 일반 적 수와 다른 경로로 결정된다.
- `LNPGameState.h`·`LNPGameMode.cpp`: `OctantGenSeed`는 Config 속성이고 0이면 시작 시 랜덤으로 정한다. 패키지에서 비제로 시드 주입과 실제 사용값을 검증해야 한다. `-FixedSeed`만으로 이 값이 1이라고 간주하지 않는다.
- `LNPOctantSpawnSubsystem.cpp`: 현재 생성 완료 조건은 8개 slot이다. 측정 대상 옥탄트 1개라는 이유로 월드 생성 자체를 1개로 줄이지 않는다.
- 기존 `Scripts/Profiling`의 네트워크·내비게이션 측정은 `-nullrhi`·코어 제한·별도 부하 구동을 사용한다. 그래픽스 측정 명령으로 그대로 복사하지 않는다.

- 비제로 월드 시드와 PCG 시드 오프셋의 주입·기록 방법을 검증한다.

### 0-D — 패키지 반복 측정과 보고

- 에디터 종료를 확인하고 `LootNPopEditor Win64 Development` 빌드를 수행한다. 패키지는 게임 타깃 Development로 별도 build/cook/stage한다.
- Build.bat·RunUAT는 처음부터 권한 확장으로 실행한다. 정확한 cook 목록에는 오버라이드 편성과 동적 로드 옥탄트·SurfaceData·종속 에셋을 포함한다.

- VSync·프레임 제한·동적 해상도를 끄고 출력·내부 해상도와 품질의 실효값을 확인한다. 그래픽스 측정에는 `-nullrhi`를 사용하지 않는다.
- 각 편성 3회 측정 후 아래 판정 규약에 따라 보고한다. 설정·바이너리·콘텐츠 버전이 다른 회차를 묶지 않는다.
- 30초~1분 경로 영상, 수치 표, 문제 → 엔진 분석 → 해결 → 측정 요약을 남긴다. 녹화는 기준선 수집과 분리한다.

## 5. 반복 측정 판정안

- 회차마다 60초 구간의 Frame·GT·RT·GPU 평균과 Frame p95를 구하고, 대표값은 회차별 값 3개의 중앙값으로 보고한다. 드로우콜은 동일 구간의 프레임당 평균을 사용한다.
- 각 주요 평균 지표의 반복 편차를 `(최댓값 - 최솟값) / 중앙값 × 100`으로 계산한다. 중앙값이 0이면 해당 지표는 판정 불가로 표기한다.
- **권장 통과 기준은 Frame·GT·RT·GPU 평균 지표 각각 편차 5% 이하**다. 초과 회차를 삭제하지 않고 열·클럭·백그라운드·씬 상태 차이를 조사한다. 재측정은 원인과 전체 회차를 남긴다.
- 1k·3k·5k는 초기 목표 초안이며 사용자 선택(2026-11-07)으로 정확한 개수 강제를 하지 않는다. 단계명은 Low·Medium·High, 보고 수는 실제 초기화 개체 수다. 일반 편성 산술값·계획 요청·계획 배치·실제 초기화를 나눠 기록한다. 부족·거부가 있으면 원인을 명시하고, 계획 수를 실제 생성 수로 대체해 쓰지 않는다.
- 화면 가시 수·표현 분포·실제 생존 수가 달라 부하 조건이 변한 회차는 원인을 분리한다. 초기 시드 일치만으로 동일 부하라 판단하지 않는다.
- 보고 표는 `Measurement.md` §5를 따르고, 16.6ms 예산 대비 비율과 회차별 값·편차를 덧붙인다.
