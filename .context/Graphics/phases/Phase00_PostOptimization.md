## 2. R-A — 개선 결과 수령과 통합 확인

네 문서와 각 개선 세션의 최종 보고를 함께 확인한다.

| 항목 | 인계 문서 | 특히 받을 결과 |
|:---|:---|:---|
| 배회 | [WanderOptimizationHandoff.md](../analysis/WanderOptimizationHandoff.md) | 시점 분산/총량/상시 비용 중 바꾼 것, 후보·실패·질의 수, 평균/꼬리 지연, 행동·복제 검증 |
| 그래플 앵커 | [GrappleAnchorOptimizationHandoff.md](../analysis/GrappleAnchorOptimizationHandoff.md) | 활성 시스템/에미터/라이트·품질 변화, GT/워커/후처리 대기·RT/GPU 영향, 가시성 회귀 검증 |
| GT 렌더 동기화 | [RenderSyncOptimizationHandoff.md](../analysis/RenderSyncOptimizationHandoff.md) | 확인한 대기 원인·원인 패스·동기화/지연/품질 정책 변화, 실제Frame/RT/GPU 개선 |
| Nav 최근접 노드 | [NavNearestNodeOptimizationHandoff.md](../analysis/NavNearestNodeOptimizationHandoff.md) | 호출자별 조회/캐시 효과, 무효화와 결과 일치, 전체GT 영향 |

각 결과에서 커밋/미커밋 변경·소스/에셋·패키지 해시·실행 조건·원자료·성공/실패 종료 코드·미검증 사항을 받는다. 반환 자료가 없거나 일부만 끝났으면 그 상태부터 기록한다. 단순히 파일이 바뀌었다는 이유로 네 개선 완료를 선언하지 않는다.

특히 배회와Nav는 공통 NavGraph/표면 조회를, 앵커와렌더 조사는 Niagara/RT/GPU 설정을 함께 바꿀 수 있다. 현재 체크아웃의 변경을 확인하고 기존 변경을 보존하면서 통합한다. 서로 다른 바이너리의 절감량을 더해 통합 성능을 추정하지 않는다. 항목별 대조 근거가 없으면 결과는 **네 변경을 합친 통합 효과**로 보고한다.

고정 시드·경로를 유지해도 재시도 주기·조회 갱신·컬링 변경으로 활동/표현 분포가 달라질 수 있다. 행동/품질이 의도적으로 달라졌다면 단순 계산 효율 향상과 구분한다. 기능 회귀나 소스 불일치가 남으면 먼저 해결하고 측정으로 넘어가지 않는다.

## 3. R-B — 빌드·별도 패키지와 기능 확인

1. 측정할 최종 소스와관련 에셋 변경을 정리하고 식별 가능한 커밋·패치·해시를 남긴다. 깨끗한 트리에서의 정규 Editor 빌드 근거를 확보한다. 로그나 `Saved/` 생성이 추적 파일을 바꿨다면 실제 상태를 다시 확인한다.
2. 에디터 종료를 확인하고 `LootNPopEditor Win64 Development` 전체 빌드 및 Game Development build/cook/stage/archive를 수행한다. Build.bat/UBT와cook/package는 외부 캐시 기록이 있으므로 처음부터 권한 확장을 사용한다. 에디터가 열려 있을 때 전체 빌드와 Live Coding을 병행하지 않는다.
3. 기존 `Saved/Graphics/Phase00Package/`와 `Phase00WanderDiagnosticsPackage_20261108/`를 보존하고 새 아카이브를 만든다. 기존 `PackageGraphicsBenchmark.ps1 -ArchiveDirectory <새 폴더>`를 이용하며 컨테이너·실행 파일·Revision3 경로 해시를 남긴다.
4. 새 패키지의 Medium을 짧게 실행해 초기 적/Pod·경로·1440p/TSR/품질 실효값·CSV 지표/개체 분할·실제 종료0을 확인한다. 사용자에게 화면·배회/표면·앵커 표시/재활성화 등 변경 관련 항목의 수동 검증을 요청한다. 짧은 실행은 성능 기준선으로 쓰지 않는다.
5. 관련 기존 자동화와 각 개선 세션의 회귀 검증을 확인한다. 계측을 유지/변경했다면 기본 비활성·실효값·계수 의미/관계를 확인한다. 계측이 폐기됐다면 근거를 받으며 옛 분석기를 새 형식에 임의로 적용하지 않는다.

같은 최종 소스의 깨끗한 트리 빌드가 이미 검증됐다면 그 식별값과 로그를 재사용한다. 소스/에셋이 달라졌으면 이전 빌드 성공으로 대체하지 않는다. 문서만 뒤에 바뀐 경우에도 무엇을 빌드했는지 정확히 남긴다.

## 4. R-C — Medium 개선 근거와 남은 병목

먼저 네 세션의 반환 자료로 필요한 비교가 충족되는지 판단한다. 충분한 같은 조건의 근거가 있으면 새 트레이스를 기계적으로 반복하지 않는다. 통합 후 자료가 부족하면 사용자 진행 확인 뒤 새 전용 폴더에 **Medium180초 워밍업/60초 경로 진단1회**를 별도 수집한다. GPU 패스나효과 절제는 필요한 질문과수집 범위를 정한 별도 단위로 둔다.

- 배회: 평균/P95/P99/최대·재선택 집중·실패/질의 수, 정지/활동 분포와 후보 생성 결과.
- 앵커: 효과GT와워커 작업·월드 후처리 대기, 활성 수·표현 품질과 RT/GPU 영향.
- 렌더: 기다리는 시간과 실제 작업/파이프라인 처리량, 원인으로 확인한 패스와 지연/품질 변화.
- Nav: 호출자별 조회 수·캐시 적중·방문 후보/할당·결과 일치와 전체GT.

새 트레이스의 캡처 시작Time을 직접 확인한다. 과거184.502898초나185.032992초를 복사하지 않는다. CSV와 이벤트를 연결할 때는 첫 프레임의 로그 이전 실행·GT 열 한 프레임 지연·월드 시각과트레이스 시각의 차이를 [측정 규약](../design/Measurement.md)에 따라 처리한다.

진단은 `DiagnosticOnly=true`·`BaselineEligible=false`로 분리하고 원본 종료 코드를 보존한다.777003이 다시 나오면 정상 종료로 표시하지 않고 원인/수집 유효성 조사 범위를 정한다. 반환 결과나 타이머 합만으로 이전3회 GT 편차의 원인을 확정하지 않는다.

## 5. R-D — 최종 바이너리의 정식 반복 측정

새 실행 파일은 기존 Low/High 통과 세트와 다른 버전이다. **이전 Low/High와 새 Medium만 묶어 공통 기준선을 완성하지 않는다.** 새 바이너리에서 Medium을 먼저3회 측정하고 재현성을 확인한 뒤, 다음 단위로 Low3회·High3회를 각각 사용자 확인 후 수행한다.

| 유지 조건 | 확인 내용 |
|:---|:---|
| 패키지·경로 | 한 최종 바이너리/컨테이너·Revision3·시드1·동일 환경 |
| 시간 | 각 회차180초 워밍업·60초 경로. 워밍업 연장을 자동 해결책으로 쓰지 않음 |
| 출력·렌더 | 2560×1440·TSR100%·품질/동적 해상도/VSync/프레임 제한 실효값. 의도적 변경은 새 기준선 조건으로 명시 |
| 계측 | CPU/GPU 트레이스·RenderDoc·배회 등 진단 계측을 끈 성능 실행 |
| 환경 | 같은 전원/화면 조건, GPU 온도·클럭·전력·사용률 기록, 백그라운드 상태 |
| 수집 유효성 | 정상 종료0·하네스complete·CSV 프레임 수/양수 지표·초기 수·활동/표현 분할·실효값 |

실행기는 기존 `RunGraphicsBenchmark.ps1`의 `-Profile`·`-PackageDirectory`·`-Repeats 3 -WarmupSeconds 180 -DurationSeconds 60`를 사용하며 매개변수의 실제 의미는 실행 전 스크립트/측정 규약으로 확인한다. 새 폴더에 원자료·환경·해시·요약을 보존한다.

각 Frame/GT/RT/GPU 평균의 반복 편차는 `(최대−최소)/중앙값×100`이며 **각각5% 이하**를 확인한다. 하나라도 넘으면 해당 회차를 삭제하거나 유리한 회차로 교체하지 않는다. 경로 구간별 부하·개체 활동·PSO/GC·온도/클럭 등과 대조하고 원인/다음 실험을 별도 단위로 정한다. 새 기준선 미통과 상태를 유지한다.

비교표에는 기존/새 버전의 회차별 값과3회 중앙값, 편차, Frame p95·예산 초과, 실제 개체 수·부하/품질 차이를 남긴다. Low/Medium/High의 기존 실제 초기 적1053/2223/3257명은 대조 대상이며 부족 수를 임의로 충원하지 않는다. 수량 일치는 개별 배치 위치 해시 일치를 뜻하지 않는다.

재현성 통과와16.6ms 목표 달성은 별개다. 재현 가능한20ms를60fps 달성으로 표시하지 않는다. 예산 초과가 남으면 정확히 보고하고 후속 렌더링 트랙의 근거로 남긴다.

## 6. R-E — 보고·영상과 Phase0 마감

네 개선의 문제 → 분석 → 변경 → 검증 결과를 전후 보고에 정리한다. 개별 대조가 없는 개선은 통합 효과로 보고하고, 변경된 행동·표현·지연 정책과 미확정 사항을 밝힌다. [Phase0 실행서](Phase00_MeasurementBaseline.md)의 완료 체크리스트를 실제 근거와 대조한다.

- 동일 조건의 세 편성 각3회와 지표별 편차·실효 조건·정상 종료 검증.
- 최종 소스의 깨끗한 트리 Editor 빌드와 게임 패키지 성공 로그/식별값.
- 기준선 보고서,16.6ms 예산 대비 수치,30초~1분 영상과 문제/분석/해결/측정 요약.
- 경로·화면·변경한 행동/효과의 사용자 확인과 미관측 범위 기록.

영상은 사용자 직접 녹화가 더 효율적이면 즉시 요청한다. 측정 중 녹화 오버헤드가 들어간 실행을 성능 기준선으로 섞지 않는다. 근거가 모이면 `Current.md`·Phase0 체크리스트·로그·`Roadmap.md` 상태를 갱신하고 사용자와 Phase0 마감을 확인한다. 체크하지 못한 항목을 자동 완료하지 않는다.

## 7. Phase0 다음 순서

기존 결정GX-003/GX-009를 유지한다.

1. **단위N:** 원점에서 먼 Niagara 월드 스페이스 정밀도/비표시 원인 조사. RenderDoc·엔진 소스로 원인을 확인하고 이미터 규칙을 정한다. JustDodge V3b의 게이트이며 그래플 앵커 성능 개선과는 별도 문제다.
2. **Phase1:** 승인 후 벤치마크 옥탄트1개·파라곤 적2~3종의 콘텐츠 투입. 현재 마네킹 상태의 확정 기준선과 전후 비교한다. 고밀도 아트를 지금 측정 조건에 미리 섞지 않는다.
3. 이후 Phase2 군중 렌더링 → Phase3 렌더 패스 → Phase4 지형 흔적 순서는 [로드맵](../Roadmap.md)을 따른다. 먼 단계의 구현을 이번 재개 단위에 포함하지 않는다.

이 문서 작성 시점에는 네 개선과후속 측정이 아직 실행되지 않았다. 이번 세션은 분석·계측·인계와 재개 절차를 기록하고 종료한다.
