> 상태: 완료(2026-11-10 사용자 확인·Phase 0 마감)

> 범위: 네 독립 개선(배회·그래플 앵커·GT 렌더 동기화·Nav 최근접)을 통합한 바이너리의 Low·Medium·High 기준선, 개선 전후 비교, 60fps 예산까지 남은 비용의 구성

## 1. 요약

- **세 편성 모두 재현성을 통과했다.** 같은 바이너리·같은 경로·같은 절차로 각 3회를 측정했고 Frame·GT·RT·GPU 편차가 모두 5% 이하다(최대 GT 3.54%).
- **GT 작업은 거의 절반이 됐다.** Medium 기준 10.57 → 5.53ms(−47.7%). 배회 프로세서의 3초 주기 스파이크가 사라졌다.
- **Frame은 거의 그대로다.** Medium 20.52 → 20.26ms(−1.3%). 프레임은 GT가 아니라 GPU에 묶여 있고, GT는 줄어든 만큼 GPU를 더 오래 기다린다.
- **60fps(16.6ms)까지 3.6~4.0ms가 모자란다.** 이 차이는 적 수와 거의 무관한 장면 렌더 비용(TSR·Lumen·직접광)에서 나온다. 다음 작업은 GPU 쪽이다.

## 4. 개선 전후 비교

전은 2026-11-07 워밍업 180초 세트(개선 전 바이너리, 회차 연속 실행), 후는 §3이다. 개선 전 세트는 냉각 대기 없이 돌렸고 Medium GT는 편차 7.23%로 재현성을 통과하지 못했다. 그래서 이 표는 **통합 효과의 참고값**이며, 개선 하나하나의 몫으로 나누지 않는다.

| 편성 | Frame 전 → 후 | GT 전 → 후 | RT 전 → 후 | GPU 전 → 후 | 드로우콜 전 → 후 |
|:---|:---|:---|:---|:---|:---|
| Low | 20.47 → 20.21 (−1.3%) | 7.77 → 4.30 (−44.7%) | 20.46 → 20.21 | 19.93 → 19.70 (−1.1%) | 578.6 → 502.3 |
| Medium | 20.52 → 20.26 (−1.3%) | 10.57 → 5.53 (−47.7%) | 20.38 → 20.25 | 19.92 → 19.75 (−0.9%) | 580.8 → 503.3 |

- High의 Frame·GPU 감소가 다른 편성보다 크다. 개선 전 세트는 회차를 연달아 돌려 뒤 회차일수록 GPU 클럭이 내려갔으므로(§7), 이 차이에는 측정 절차 차이가 섞여 있다. 개선 효과로 주장하지 않는다.
- 같은 기간 측정 옥탄트의 지면 재질과 SurfaceData도 바뀌었다(`ed8c930`·`6461246`·`0e433b8`). 전후 차이는 **네 개선 + 콘텐츠 변경**의 결과다.

## 5. 네 개선 — 문제 → 분석 → 변경 → 검증

네 개선은 각각 별도 세션에서 해당 범위 지표만으로 검증했다. 상세는 각 인계 문서가 원본이다.

### 5.1 배회 프로세서 — [배회 최적화 인계](WanderOptimizationHandoff.md)

- **문제:** Medium 진단에서 배회 처리가 평균 2.09ms였고, 약 3초마다 24ms 안팎의 스파이크가 났다.
- **분석:** 실패한 배회 재시도가 같은 3초 주기에 맞춰 한 프레임에 몰렸다(만료 상위 20프레임 평균 103.75건). 후보 실패율은 57%였고, 실패할 때마다 비싼 충돌 질의를 반복했다.
- **변경:** 실패 재시도에 지수 백오프와 개체별 지터를 넣고, 한 실행의 재선택을 16건으로 묶었다. 막힌 후보는 거부하지 않고 잘라서 쓰고, 후보 시도는 4회에서 2회로 줄였다. 싼 검사를 비싼 검사 앞에 두고, 정지한 개체는 매 프레임 재계산하지 않는다.
- **검증:** 패키지 진단 1회에서 평균 2.088 → 0.758ms, P99 15.84 → 1.24ms, 5ms 이상 실행 76 → 0회. 자동화 32건 통과, 1P·2P PIE 사용자 확인.
- **행동 변화(수용):** 초당 재선택이 178.5 → 79.2로 줄었다. 정지가 3~6초로 길어졌고, 뭉친 곳에서는 제자리에 서 있는 시간이 늘 수 있다. 사용자가 자연스럽다고 보고 받아들였다. 벽보행 드론이 오목한 구석에서 떨던 결함도 함께 고쳤다.

### 5.2 그래플 앵커 효과 — [그래플 앵커 최적화 인계](GrappleAnchorOptimizationHandoff.md)

- **문제:** `NS_GrappleAnchor`가 GT에서 프레임당 0.44ms를 썼고, 이 효과를 포함한 워커 작업을 GT가 기다리는 사례가 있었다.
- **분석:** 앵커마다 CPU 에미터 4개, 동적 라이트, 카메라 데이터 인터페이스, 거리 확대, 힘·속도 솔버가 매 프레임 돌았다. 멀리 있는 앵커도 시뮬레이션이 계속됐다.
- **변경:** CPU 에미터 하나, 220cm 스프라이트 한 장으로 줄이고 원·고리·각도는 머티리얼(`M_LNPAnchorDistance`)에서 그린다. 실효 사용 거리의 2배 밖에서는 시뮬레이션을 멈춘다. 거리 계산은 기존 상호작용 컴포넌트의 것을 재사용한다.
- **검증:** 패키지 진단 1회에서 앵커 GT 직접 비용 0.440 → 0.054ms/프레임(−87.7%). 시각 테스트 통과, 여러 차례 PIE를 거쳐 사용자 최종 수용.
- **표현 변화(수용):** 화려한 장식이 단일 스프라이트와 접근하면 완성되는 고리로 바뀌었다. 드로우콜 감소(약 580 → 502)에도 기여한 것으로 보이지만 대조 측정은 없다.

### 5.3 GT 렌더 동기화 — [렌더 동기화 최적화 인계](RenderSyncOptimizationHandoff.md)

- **문제:** CPU 진단에서 GT가 렌더링을 기다리는 `Sync_RenderingThread`가 프레임당 9.27ms였다.
- **분석:** 배회·앵커·Nav 개선으로 GT 작업이 절반이 돼도 Frame은 0.2ms 이내로만 변했다. 렌더 해상도를 낮추면 GT 대기가 해상도와 함께 줄었다(14.6 → 7.6 → 5.2ms). 가림 질의 버퍼를 늘려도(D4) Frame이 줄지 않았다. 따라서 이 대기는 동기화 오버헤드가 아니라 **GPU 처리량 부족이 역류한 대기**다.
- **변경:** 동기화 설정은 바꾸지 않았다. 바꾸면 대기 위치만 옮겨 가고 입력 지연만 는다. 대신 GPU 패스를 큐별로 분해하는 진단 경로(trace region, 진단 CVar 인자)를 추가했다. 이 경로는 인자를 주지 않으면 비용이 없고, 진단 회차는 `performance_eligible=false`로 기준선에서 빠진다.
- **검증:** D0~D5 진단 6회. 결과 패스 표는 §6이다.
- **보류 결정:** TSR 히스토리 100%(D5에서 Frame −1.63ms)와 Lumen 조정은 프로토타입 에셋에서 화질을 판단할 수 없어, 벤치마크 콘텐츠(Phase 1) 뒤로 미뤘다. 기준선은 Epic 기본값이다.

### 5.4 Nav 최근접 노드 — [Nav 최근접 노드 최적화 인계](NavNearestNodeOptimizationHandoff.md)

- **문제:** 직선 보행 중인 적이 매 프레임 시작·목표 위치로 최근접 Nav 노드를 조회했다(프레임당 0.21ms).
- **분석:** 호출 하나가 느린 게 아니라, 같은 입력으로 300cm 구를 감싸는 넓은 격자 창을 매 프레임 다시 훑었다. 목표 캐시 적중은 0%였다.
- **변경:** 지난 프레임의 결과 노드를 힌트로 넘겨 탐색 반경을 그 거리로 줄였다. 최근접과 동률 규칙이 그대로라 결과가 같다. 호출당 힙 할당도 없앴다.
- **검증:** 힌트 결과 일치 자동화 1232점·117589회 조회 전부 일치. 패키지 진단 1회에서 호출당 3.72 → 1.27μs. 같은 시기 실패한 생산 Nav 자동화 2건은 이 변경과 무관한 콘텐츠 변화 탓이었고 `6951110`에서 보완했다.
- **행동 변화:** 없음.

## 7. 측정 절차에서 고친 것 — 노트북 전력 하향

- **문제:** 새 바이너리로 Medium 3회를 연속 실행하자 Frame·GT·RT·GPU 편차가 모두 5%를 넘었다(5.99 / 5.09 / 5.99 / 6.12%).
- **분석:** 회차마다 Frame·GPU가 단조 증가했고, GPU 클럭(2233 → 2087MHz)과 전력(89.7 → 78.1W)이 같은 비율로 내려갔다. 1초 간격 기록에서 전력은 부하 시작 뒤 약 5분 동안 92~95W를 유지하다 78~81W로 떨어졌다. GPU 시간에 클럭을 곱해 보정하면 세 회차 편차는 0.54%였다. 장면의 작업량은 같았고 흔들린 것은 클럭이었다.
- **변경:** 회차를 하나씩 따로 실행하고, 각 회차 전에 GPU가 55°C·15W 이하를 60초 연속 유지할 때까지 기다린다. 회차 하나(약 4분)가 전력 하향 전에 끝난다. 규칙은 [측정 설계](../design/Measurement.md)에 넣었다.
- **측정:** 같은 바이너리로 재측정한 Medium 편차는 0.31 / 2.11 / 0.31 / 0.35%이고, 회차 사이 클럭은 2245~2251MHz로 같았다. Low·High도 같은 절차로 통과했다. 연속 실행 세트는 실패 기록으로 보존했다(`Saved/Profiling/Graphics/Phase00/PostOptMedium_20261109_130035/`).

## 8. 미관측 범위와 한계

- **전투 없음.** 벤치마크 경로는 배회만 있다. 추격·공격·투사체·피격 효과의 비용은 이 기준선에 없다.
- **폰 고정.** 하네스는 카메라만 움직인다. 앵커 거리 컬링의 활성·중단 전환 비용과 플레이어 이동에 따른 Actor 승격·강등은 측정하지 않았다.
- **1인·Development.** 2인 리슨 서버의 복제 비용과 Shipping 빌드는 측정하지 않았다.
- **개선별 몫은 나누지 않는다.** 네 개선은 각자 범위 지표로만 검증했고, 통합 바이너리에서는 합친 효과만 보인다. 개선 전 세트는 냉각 대기 없이 측정해 절차 차이도 섞여 있다.
- **콘텐츠는 프로토타입이다.** GPU 패스 구성은 벤치마크 콘텐츠가 들어오면 바뀐다. 그때는 새 패키지로 D0부터 다시 잡고 이번 수치와 직접 섞지 않는다.
- **측정 옥탄트가 하나다.** Acropolis 외 옥탄트의 비용은 대표하지 않는다.
- 활성 NPC 평균이 회차마다 다르다(예: Medium 3회차 111.8, 앞 두 회차 약 173). 타이밍 편차는 기준 안이지만 원인은 확인하지 않았다.
- 트레이스를 켠 실행은 종료 코드 777003을 낸다. 기준선 실행은 트레이스를 쓰지 않아 모두 0이다. 777003의 원인은 확인하지 않았다.
