# 그래플 앵커 효과 최적화 인계

> 상태: 비주얼 최종 수용·최적화 구현 및 자동 검사 완료 · 앵커 GT 패키지 진단 비교 완료(정식 기준선 아님)
> 갱신: 2026-11-08
> 목적: 사용자가 별도 세션에서 `NS_GrappleAnchor`와 관련 작업 대기를 조사·개선할 근거

## 1. 확인한 문제와 해석 범위

그래플 앵커 Niagara는 배회 외의 후속 조사 후보다. 기존 CPU 진단에서 GT의 효과 처리와, 해당 효과를 포함한 워커 작업 때문에 GT가 기다린 대표 사례를 확인했다. **효과 내부의 어느 단계가 비싼지, 전체 월드 후처리 대기의 얼마를 차지하는지는 미확정**이다.

| 관측 항목 | 측정값 | 의미 |
|:---|---:|:---|
| GT `NS_GrappleAnchor` | 66194회·포함1.312407초·제외1.295940초 | GT2983프레임으로 나누면 포함0.4400ms/프레임 |
| 전체 스레드 `NS_GrappleAnchor` | 1643633회·제외8.090761초 | 병렬 스레드 합계다. 같은 길이의 프레임 지연이나 고유 앵커 수를 뜻하지 않음 |
| 전체 `WaitForTasks` | 10.856891초·3.6396ms/프레임 | 아래 월드 후처리와 틱 완료 경로가 섞임 |
| 월드 후처리 분기 | 약7.31초·2.45ms/프레임·67.31% | GUI 반올림 값. 이 전체를 앵커 효과 비용으로 귀속하지 않음 |

대표 최대 사례의 GT 대기는239.319501~239.322189초·약2.69ms다. `OnWorldPostActorTick → WaitUntilTasksComplete`에서 **Task15523600 하나**를 기다렸다. 해당 작업은 Foreground Worker(Standby #1)에서239.319253~239.322174초·약2.92ms 실행됐고 내부에 `NS_GrappleAnchor` CPU 범위를 확인했다. 구체적인 C++ 작업 타입과 내부 단계별 비중은 확인하지 않았다. 대표 최대 사례가 평균 사례를 보장하지도 않는다.

## 2. 코드·에셋 진입점

- [LNPGrappleAnchor.h](../../../Source/LootNPop/WorldDevice/LNPGrappleAnchor.h): 효과 컴포넌트와 앵커 인터페이스.
- 에셋: `/Game/WorldDevice/BP_GrappleAnchor`, `/Game/Effects/WorldDevice/NS_GrappleAnchor`.
- [월드 장치 설계 §9](../../TechDesign_WorldDevice.md#9-앵커-시각-표현과-비가시-회귀-2026-10-08): BP 배선과 이전 비표시 회귀의 원본 기록.

기존 설계 문서는 Core/Halo/Ping/Light의 CPU 에미터·무한 루프와 라이트 렌더러, 거리 컬링 비활성 상태를 기록한다. **이번 인계 작성에서 에셋 내부를 라이브 조회한 것은 아니므로** 최적화 세션에서 실제 에셋/실효 설정을 먼저 확인한다.

## 3. 별도 세션의 조사·개선 후보

| 조사 지점 | 확인할 근거 |
|:---|:---|
| 실제 활성 시스템 수 | 총 앵커 수·활성/비활성·카메라 거리·가시성별 수. 타이머 Count를 개체 수로 쓰지 않음 |
| CPU 단계 분해 | 시스템/에미터/파티클 갱신·동적 렌더 데이터·작업 수와 동기화의 비중 |
| 거리·가시성별 갱신 | 효과 중요도·갱신 빈도·컬링/재활성화·Bounds 정책과 시각 품질 |
| 에미터·렌더러별 비용 | Core/Halo/Ping/Light를 각각 분리해 CPU/GT 대기/RT/GPU 영향 측정. 한꺼번에 끈 결과로 특정 에미터를 지목하지 않음 |
| 다수 소형 작업 | 앵커별 작업 분산/배치가 작업 수·스케줄링·월드 후처리 임계 경로에 미치는 영향 |

CPU 시뮬레이션의 GPU 전환은 검토 후보일 수 있으나, 현재 Medium GPU도 약19.92ms로16.6ms 예산을 넘는다. CPU 시간 감소와GPU 비용 이동을 함께 확인해야 한다. 어느 방법도 이 문서에서 확정하지 않았다.

## 4. 보존할 동작과 검증 기준

- 과거 `EffectComponent.bAutoActivate=false`로 효과가 완전히 안 보였어도 상호작용과 그래플 이동은 동작했다. **게임 기능 정상만으로 시각 회귀가 없다고 판정하지 않는다.** 위 기존 시각 테스트는 에셋 연결·자동 활성화·가시성을 확인한다.
- 구면 월드의 여러 구역·거리·카메라 회전에서 효과 표시와 재활성화를 확인한다. 앵커 발견성·상호작용 프롬프트·그래플 이동·복제된 존재/ID를 함께 보존한다.
- 효과 개수·입자 수·라이트·갱신 빈도가 바뀌면 시각 품질 차이를 기록한다. 효과를 없애서 줄어든 부하와 같은 표현의 계산 효율 향상을 구분한다.
- 같은 패키지 측정 조건에서 GT 효과 시간, 워커 작업 합, 후처리 대기 분포, Frame/RT/GPU를 비교한다. 대표 최대 대기 한 건만으로 개선을 판정하지 않는다.
- PIE·Niagara 편집기 조작이 빠르면 사용자에게 바로 요청한다. 기존 시각 테스트와 수동 품질 확인은 역할이 다르다. 이 인계 단위에서는 새 실행·에셋 변경·테스트를 하지 않았다.

## 7. 거리 표현 재설계 구현 (2026-11-08)

사용자는 원근감 개선·접근에 따라 완성되는 고리·저렴한 표현을 승인했다. 화려한 장식을 유지하는
에미터 통합 대신 `Core` CPU 에미터 하나·220cm 고정 크기 스프라이트 한 장으로 줄였다.
`M_LNPAnchorDistance`가 Core와 고리를 함께 그리며 Halo·Ping·Light, 거리 확대·카메라 DI,
Core의 힘/속도 솔버를 제거했다. 시스템 현재 프레임 데이터 요구 해제, 보간 스폰 해제,
Fixed Bounds 각 축 ±160cm를 적용했다. 머티리얼은 Unlit Translucent·깊이 검사 유지,
별도 텍스처 에셋·동적 라이트·추가 UI가 없다. 원형·고리·각도는 작은 스프라이트의 픽셀 셰이더에서 계산한다.

### 거리 정책과 실행 경로

- R은 앵커별 실효 최대 사용 거리다. 폰 거리 d에서 접근 진행률은 `clamp(2-d/R, 0, 1)`.
- 최대 거리 밖의 고리는 마지막 틈을 남기며, 기존 최소·최대 거리 조건을 충족할 때만 완성한다.
- 1.6R~2R에서 페이드, 2R 이상이면 Niagara 실행 중단, 다시 접근하면 파라미터 설정 후 재활성화.
- 기존 `ULNPInteractionComponent`의 거리 계산을 광역 상호작용 컷 전에 재사용한다.
  로컬 플레이어만 표현을 갱신하며 Actor Tick·타이머·추가 LOS·네트워크 상태는 추가하지 않는다.
- 시각 상태는 `User.DistanceVisualState`로 전달한다. 작은 변화는 1/255 허용 오차로 파라미터 갱신을 생략하지만
  거리 충족 플래그 전환과 활성화·비활성화는 즉시 처리한다.
- Actor 숨김·레지스트리 제거·AnchorID·서버 판정·Mover·F 프롬프트 조건은 변경하지 않았다.

### 변경 범위와 복구점

앵커 `.cpp/.h`, 기존 상호작용 컴포넌트의 거리 갱신 연결, 앵커 시각 테스트,
`NS_GrappleAnchor`, `BP_GrappleAnchor` 자동 활성화 정책, 새 `M_LNPAnchorDistance`, 본 문서와 월드 장치 설계 §9.
기존 에셋 복사본은 `Saved/Diagnostics/GrappleAnchor/DistanceVisual_20261108/`.
다른 세션의 Enemy·SurfaceNavigation 수정은 편집하지 않았다. 공용 에디터의 C++ 컴파일에는
해당 세션의 미커밋 코드도 포함되므로 빌드 결과와 앵커 단독 성능 효과를 구분한다.

### 검증 상태

- 새 머티리얼 컴파일 성공. Niagara `UpToDate`, 오류·경고 없음.
- C++ Live Coding 성공(공용 에디터의 다른 세션 미커밋 코드 포함).
- `LootNPop.WorldDevice.GrappleAnchor.VisualAsset`, `DistanceVisualState` 2/2 통과, 오류·경고 없음.
  거리 검사는 미설정·발견 한계·페이드·접근 진행·최소/최대 경계·짧고 긴 마커 범위를 확인한다.
  첫 실행의 페이드 비교 허용 오차가 너무 작아 실패한 검사를 `KINDA_SMALL_NUMBER`로 수정 후 통과했다.
- 의존성 재조회: Sprite Renderer 1종, Data Interface와 Dynamic Input 모두 0개.
- 세 에셋의 디스크 파일 확인. BP는 저장 API가 파일을 쓰지 않아 앵커 BP 에디터의 Save로 저장 후 파일 변경을 확인했다.
- 자동화 결과·최종 에셋/소스 해시는 `Saved/Diagnostics/GrappleAnchor/DistanceVisual_20261108/Validation.json`.
- 사용자 최종 PIE 확인: Core/고리 진행·사용 거리 안 완성·크기·색상·좌우 이동 안정성,
  주기적 사선 튐 해소·원거리 소실 후 복귀를 수용했고 비주얼 작업 종료를 요청했다.
  모든 마커 범위·최소 거리·화면 가장자리·낮은 품질·호스트/게스트 조합의 전수 검증을 뜻하지 않는다.
- 이 변경은 표현 단순화도 포함한다. 원래와 같은 시각 품질의 계산 효율 향상만으로 분류하지 않는다.
- 새 패키지·GT/워커/후처리 대기/RT/GPU 전후 측정은 아직 없다. 기존 Phase0·기준선 판정은 유지한다.

### 첫 PIE 피드백과 가시성 보정

사용자 확인: 색이 너무 연해 가시성이 낮고, 고리가 너무 크며, 접근 진행이 완성되는 호보다
흐릿한 전체 고리가 진해지는 변화로 읽혔다. 최초 표현의 시각 검증은 미통과로 기록한다.

- 머티리얼의 희미한 배경 전체 고리를 제거했다. `ring * step(angle, progress)` 부분만 알파로 남긴다.
- Additive에서 Translucent로 바꿔 밝은 배경이 고리와 Core의 색을 씻어내는 문제를 줄이는 방향으로 조정했다.
  청록색은 흰색에 가깝게 바꾸지 않고 유지하며, 발광 밝기는 범위 밖3.5·범위 안4.5를 쓴다.
- 스프라이트300→220cm, Core 외경 약75cm 유지, 고리 중심선 지름216→138.6cm,
  선 두께7.5→9.9cm. 범위 밖 마지막 틈은4%→6%로 넓혀 완성 상태와 구분한다.
- Bounds ±220→±160cm. 에미터·입자·스프라이트·패스 추가와 C++ 수정은 없다.
- 머티리얼 재컴파일 성공, Niagara UpToDate·오류/경고 없음. 두 에셋 디스크 저장 확인.
- 기존 거리 자동화 검사는 C++ 계산·배선 검증이며 사용자 체감을 보장하지 않는다. 보정 후 PIE 재확인 대기.
- 보정 전 두 에셋은 `Saved/Diagnostics/GrappleAnchor/DistanceVisual_20261108/BeforeVisibilityFeedback/`에 보관했다.

### 두 번째 PIE 확인과 테두리 보정

사용자 확인: 접근에 따른 고리 완성과 크기는 적절하고 흐릿함은 해결됐다. 다만 색이 칙칙하고
밝은 배경 외에서는 눈에 잘 띄지 않았다. 사용자는 밝은 본체·어두운 테두리를 같은 스프라이트에서
계산하는 방식을 승인했다. 크기·진행·거리 정책과 C++는 유지했다.

- `M_LNPAnchorDistance` 하나만 수정했다. 본체 청록색 `(0.22, 0.85, 1)`·밝기5/6(범위 밖/안).
- 기존 Core·고리의 거리 계산을 재사용해 넓힌 마스크를 만들고, 바깥쪽에 거의 검은 테두리를 합성한다.
  호의 시작·끝도 각도 마스크를 조금 넓혀 감싼다. 미완성 전체 원을 다시 그리지 않는다.

### Core 파이와 좌우 이동 보정

사용자가 PIE에서 현재 비주얼을 수용한 뒤 Core도 고리와 함께 파이 모양으로 차오르게 요청했다.
동시에 정지할 때는 정상이나 좌우 이동하며 앵커를 보면 모양이 찌그러지는 현상을 보고했다.

- `M_LNPAnchorDistance`만 수정했다. Core와 고리의 합집합에 같은 각도 마스크를 적용하고,
  넓힌 테두리 마스크에도 같은 호 마스크를 적용했다. 사용 거리 안의 완성 원·크기·색·노출 보정은 유지한다.
- 렌더러는 Automatic→FaceCamera/Unaligned로 해석되는 상태이고 SpriteFacing/Alignment/Velocity 바인딩은 없다.
  현 엔진의 이 방향 계산은 이미 카메라 평면을 사용한다. 불필요하게 Facing 설정이나 NS 에셋을 바꾸지 않았다.
- 머티리얼의 `bOutputTranslucentVelocity`가 false였으므로 true로 켰다. 배경 깊이로 재투영하는 대신
  앵커의 깊이·속도를 출력하게 하는 보정 후보이며, 이동 중 찌그러짐의 해결 여부는 아직 미확정이다.
- Niagara MotionVectorSetting은 AutoDetect, 프로젝트 기본값은 Precise다. 별도 시뮬레이션이나 프레임 데이터 의존성은 추가하지 않는다.
- 기존 Velocity 패스에서 드로우·깊이 출력 비용이 추가된다. 무료 최적화로 분류하지 않는다.
- AfterDOF·깊이 검사를 유지하고 전역 AA·모션 블러는 변경하지 않았다. 엔진에서 AfterMotionBlur 경로는
  깊이 검사 방식이 달라 벽 너머 표시 회귀를 피하기 위해 적용하지 않았다.
- 머티리얼 컴파일 성공·모션 벡터 플래그 재조회·파일 해시 변경·디스크 저장 확인. C++·다른 세션 파일은 수정하지 않았다.
- 사용자 PIE 대기: 1R~2R에서 Core 파이/고리 동기 진행, 1R 안에서 완성, 좌우 이동 중 형태 안정성,
  지형 가림·프롬프트·거리 페이드. 일반적인 모션 블러와 TSR 재투영 변형을 구분해 평가한다.
- 변경 전 머티리얼은 `BeforeCorePieAndVelocity/`에 보관했다. 이전 자동화 2/2는 변경하지 않은 C++ 경로의 결과다.

### Core 축소와 주기적 사선 튐 보정

- 원거리 중단·재진입은 기존 C++의 `DeactivateImmediate`와 Reset 활성화를 사용한다. 수명 종료를 기다리지 않는다.
- 머티리얼 컴파일 성공. Niagara 최종 `UpToDate`, compiling/stale/errors/warnings 모두 false.

- 복구점: `Saved/Diagnostics/GrappleAnchor/DistanceVisual_20261108/BeforePersistentParticle_Resumed/`.

## 8. 최종 수용과 후속 측정 범위 (2026-11-08)

사용자가 마지막 PIE에서 중앙 파이 크기·사선 튐·거리 컬링 후 복귀 모두 정상이라고 확인하고
비주얼 개선을 마무리하기로 했다. 5초 재생성을 없앤 후 튐이 사라졌다는 관측은 확보했으나,
이전 프레임 모션 벡터 초기화의 구체적 엔진 결함을 추적·증명한 것은 아니다.

성능 비용원을 줄이는 구현은 적용됐다: CPU 에미터4→1, 컬러 스프라이트3개와 라이트 표현→스프라이트1장,
Camera DI와 현재 프레임 의존성·거리 확대·힘/속도 솔버 제거, 2R 이상 시뮬레이션 중단,
최초 입자 유지, 기존 상호작용 거리 계산 재사용, Bounds 축소.
비주얼 요구로 SDF/각도·테두리 연산, 기존 노출 버퍼 조회, Velocity 패스 드로우가 추가됐으므로
이 항목을 포함한 최종 버전의 순절감량을 측정해야 한다.

비주얼 수용 시점에는 패키지 전후 비교를 하지 않았다. 이후 사용자가 앵커 GT만 평가하도록 범위를
정했고, 결과는 §9에 기록했다. 월드 후처리 대기 평균/꼬리·RT/GPU는 이번 판정에서 제외했다.
월드 후처리 대기 전체2.45ms를 앵커 절감 가능량으로 귀속하지 않는다.

다음 단계는 [개선 후 재개 절차](../phases/Phase00_PostOptimization.md)의 최종 패키지 검증과
필요한 동일 조건 비교다. 여러 세션의 변경이 섞인 빌드 비교는 통합 효과로 보고하고,
앵커 단독 절감량은 통제된 대조 없이는 주장하지 않는다. 이 상태 답변 시점에 새 장시간 실행은 시작하지 않았다.

### 후속 측정 범위 확정 (2026-11-08)

사용자가 다른 세션의 GPU 병목 분석과 변경 혼재를 고려해 **앵커 GT 직접 비용만** 평가하도록 범위를 정했다.
전체 Frame·GT·RT·GPU, 배회/Nav의 효과, 월드 후처리 대기 감소는 이번 비교의 판정 대상에서 제외한다.

- 동일 Medium 편성·시드·카메라 경로·180초 워밍업/60초 캡처의 패키지 진단1회를 별도 폴더에 보존한다.
  정식 반복 기준선으로 분류하지 않는다.
- 기존 `NS_GrappleAnchor`의 GameThread 포함/제외 시간을 같은 이름으로 비교한다.
  기존 진단 약0.44ms/프레임은 Niagara 구간 값이며 앵커 관련 전체 비용을 뜻하지 않는다.
- 새 C++ 거리 상태·색 갱신·활성/중단 비용을 `LNPGrappleAnchor_DistanceVisual` CPU 추적 구간으로 기록한다.
  Niagara 시간과 따로 보고하고, 합산 시 중첩 구간을 이중 집계하지 않는다.
  기존 상호작용 루프의 거리 계산·형변환 등 함수 밖의 미세 비용은 이 구간에 포함되지 않는다.
- 각 합계는 앵커 이벤트 횟수가 아닌 같은 구간의 GT 프레임 수로 나눈다. 실행당 시간과 프레임당 시간을 구분한다.
  꼬리값을 보고한다면 전체 GT가 아닌 프레임별 앵커 구간 합계의 값으로 한정한다.
- 거리 컬링과 표현 단순화가 함께 반영된 실제 경로 비용이다. 혼재 빌드의 스케줄링 차이와 진단 계측 오버헤드가
  남으므로 순수 알고리즘 개선량이나 전체 프레임 향상으로 일반화하지 않는다.

기존 진단을 재집계해 GT2983프레임·앵커66194회·합계1.3124069초로 기존 통계와 일치함을 확인했다.

P95/P99는 프레임별 합계의 최근접 순위이며 전체 GT의 꼬리값이 아니다. 기존 실행의 비정상 종료777003과
진단 전용 분류는 그대로 유지한다. 재집계가 새 최적화 후 측정을 대신하지 않는다.

`AnalyzeAnchor.py`는 GameThread 구간과 프레임 경계를 검증하고, 합산 시 중첩된 자식 구간을 제외한다.

실패했다(`LNK1104`, `EditorBuild_Attempt1.log`). 에디터를 임의 종료하지 않고 사용자 종료 확인을 요청했다.

### 해석과 제한

- **이 하네스는 카메라만 이동시키고 폰은 고정한다.** 거리 컬링은 `UpdateDistanceVisual`에 전달되는 폰 위치를 따른다.
  따라서 이번 결과는 고정 폰 주변에서의 비용이며, 카메라 경로에 따른 접근·이탈 비용을 측정한 것이 아니다.
  실제 이동 중의 빈번한 활성/중단과 다른 앵커 밀도까지 대표한다고 주장하지 않는다. 비주얼·재진입 기능은 기존 사용자 PIE 수용 근거를 유지한다.
- 캡처/CSV는2996프레임·`complete`로 완료됐지만, 종료 과정에서 프로세스 코드777003이 반환됐다. 로그에는 정상 종료 요청과
  `LogExit: Exiting`까지 남았고 원인은 확인하지 않았다. 기존 진단도 같은 코드였다. 두 실행 모두 진단 전용이며 정상 종료 검증이나
  정식3회 기준선 통과로 취급하지 않는다. 새 트레이스는 Insights 분석/내보내기를 완료했다.
- CPU 분석의 `Frame` 메타데이터 타이머 중복 제거 경고를 보존했다. 분모는 해당 타이머가 아닌 `FEngineLoop::Tick`으로 검증했다.
- 새 추적 구간 자체의 진단 오버헤드는 이후 값에 포함됐다. 함수 밖의 기존 상호작용 순회·거리 계산·추가 형변환은 범위 밖이다.
- 다른 세션의 변경이 섞인 단일 진단 쌍이다. **앵커 구간의 관측 비용 감소**로 보고하며 순수 단일 변경의 인과 효과로 확정하지 않는다.
  사용자 요청대로 전체 Frame/GT·RT·GPU, 배회/Nav, 워커 합계와 월드 대기 변화는 평가하지 않았다.
