# V4a 작업 기록

## 2026-11-06 — 지연 중 순보 체감 확인·관전 Ghost 결함 조사

- 필수 세 문서·비주얼 설계·검증 규약·로드맵·V3a 실행서를 읽고 V4a에 착수했다. 성공 큐, 카메라 노드, 무적 창 기록, 클라이언트/서버 투사체 처리와 대상 에셋 파일 존재를 확인했다.
- 사용자 보고: `net.PktLag=50`에서도 저스트 회피가 대시 모션과 함께 잘 보이며, 눈에 보이는 효과만으로는 0과 구분하기 어려울 만큼 자연스럽다. V-05 체감 확인으로 기록하고 J-007을 유지한다. 이번에는 큐 지연 수치를 재측정하지 않았다.
- 별도 보고: 게스트 화면에서 호스트의 저스트 회피를 관찰하면 Ghost 투사체가 계속 날지 않고 사라지는 것으로 보인다.
- 코드 조사: `LNPCharacterMoverComponent.cpp`의 `ExecuteDash`는 Authority·AutonomousProxy만 `DodgeIFrameExpiryTime`을 기록한다. `LNPProjectileProcessors.cpp` 클라이언트 분기는 원격 플레이어도 후보에 넣고 기록되지 않은 무적 창을 읽으므로, 캡슐에 닿으면 `FLNPGhostDestroyCommand`와 예측 임팩트를 실행할 수 있다. 서버의 `Dodged`·`JustDodged`는 관통한다. 호스트는 소급 판정 대상이 아니므로 J-019 예외와 구분한다. 특정 탄의 서버/클라이언트 로그 대조는 미실시다.
- 최소 수정 후보는 원격 플레이어에 대한 선행 Ghost 소멸을 생략하고 기존 서버 착탄 큐에 맡기는 것이다. 일반 명중 시 탄이 서버 큐 도착까지 더 진행해 보이는 절충점이 있어 사용자에게 설명하고 다음 구현 단위 진행 여부를 확인한다. 아직 코드·에셋은 수정하지 않았다.
- Unreal MCP의 읽기 호출과 프로젝트 스킬 목록 조회가 성공했다. 관련 추가 스킬은 없었으며 조회 시 PIE는 종료된 상태였다. 문서 변경만 수행해 빌드는 실행하지 않았다. 기존 EliteNPC 등 다른 작업의 수정은 건드리지 않았다.
- PktLag 0 복원, ADS 경계 및 기존 미확인 경계는 별도 보고가 없어 미확인으로 유지한다. 다음 행동은 [V4a 실행서](../phases/PhaseV4a_VisualReadability.md)를 따른다.

### 수정 후보 재검토 — 기존 대시 시작 시각 재사용

- 사용자가 공통 무적 길이와 대시 몽타주 재생 정보로 원격 무적 구간도 알 수 있는지 질문했다. 재조사 결과 `FLNPDashCooldownModifier`는 엔진 기본 `NetSerialize`를 통해 `StartSimTimeMs`를 복제하며, 프로젝트의 `UpdateSyncedMontageState`가 이미 현재 Mover 시뮬레이션 시각과의 차로 몽타주 시작 위치를 계산한다.
- 기존 정보만으로 원격 캐릭터의 대시 경과 시간을 구할 수 있으므로, 별도 동기화가 더 큰 범위라고 단정한 앞선 설명을 정정했다. 서버 착탄 대기 제안은 보류하고 이 정보를 재사용하는 코스메틱 무적 복원을 우선 검토한다. 수신 시점부터 창을 새로 여는 것은 잘못이며, 시계 변환·늦은 상태 수신·원격 게스트 누름 추정 보정의 경계는 남는다. 아직 코드 변경은 없다.

### 원격 코스메틱 무적 구현·검증

- 사용자가 원격 무적 판정 작업을 승인했다. 정보 연결 누락을 먼저 고치고, 수신 전 오소멸은 재검증 뒤 판단하기로 했다(J-025). 소멸 보류·복구·서버 착탄 대기로 정책을 바꾸지 않았다.
- 기존 `FLNPDashCooldownModifier::StartSimTimeMs`와 새 `DodgeIFrameEndOffsetMs` 한 값으로 원격 창을 복원했다. 오프셋은 `(IFrameDuration − U) × 1000`이며, 서버 기존 판정과 같은 `U`를 재사용해 원격 게스트의 누름 보정까지 포함한다. 서버·소유 클라이언트의 회피 판정은 기존 `ExecuteDash` 경로를 유지한다.
- 프레임 확정 후 SimulatedProxy 분기에서 남은 시간만 로컬 월드 시계로 옮기고, 대시 부재·시작 전·만료는 -1로 갱신한다. 몽타주 부재·이미 재생함 검사보다 먼저 실행한다. 기존 Ghost 무적 검사·`DodgedEntity` 재접촉 제외를 그대로 소비한다. 상세 공식은 아키텍처 §2.3에 기록했다.
- Live Coding 성공: UHT 포함 UBT 12개 작업·84.35초. 에디터 자동화 `LootNPop.Combat.JustDodge.ProxyWindow` 1건 성공(0.0168초, 오류·경고 0). 시작 전·미시작·늦은 수신·만료·쿨다운 잔류·몽타주 없음·서버 보정·직렬화 왕복·롤백 복사·음수 종료 오프셋을 확인했다. 실제 네트워크 패킷 순서나 Ghost 궤적까지 자동 검증한 것은 아니다.
- 사용자에게 필요한 변경 저장·에디터 종료를 요청했고 종료 확인 뒤 프로세스 부재를 확인했다. 권한 확장으로 정규 `LootNPopEditor Win64 Development -WaitMutex -NoHotReloadFromIDE -DisableAdaptiveUnity` 빌드 성공(10개 작업·42.82초). 다른 작업의 문서 변경이 있는 트리이므로 깨끗한 트리 빌드로 기록하지 않는다.
- 사용자에게 에디터 재실행·TestMap03 리슨 2인·미리보기 0·로그 1·두 창 PktLag 0/50에서 호스트 회피의 관통, 일반 명중, 뒤 지형 착탄을 확인하고 종료 시 양쪽 PktLag를 0으로 복원하도록 요청했다. 결과는 대기 중이며, 다음 구현 단위는 이 결과를 정리한 뒤 다시 확인한다.

### 반경 튜닝·난도 체감 질문 조사

- 사용자는 관통 재검증 결과 대신, `ParryRadius`를 크게 늘려도 저스트 회피가 쉬워지지 않고 이전보다 어렵게 느껴진다고 질문했다. 관통 검증 통과로 기록하지 않는다.
- 변경분 재검토: `Judge`·저스트 창·무적 길이·반경 소비 조건·소급 판정에는 이번 단위의 조건/수치 변경이 없다. 기존 서버 업링크 계산을 대시 상태 작성 위치로 옮겨 같은 값으로 프래그먼트와 복제 오프셋을 기록한다. 새 프래그먼트 갱신은 SimulatedProxy 분기에서만 실행한다.
- 순수 엔티티 공격은 공격자 `EntityAttackConfig.ParryRadius`를 읽는다. 투사체는 발사체 공유 프래그먼트에 복사하고, 피격자 캡슐을 그 반경만큼 팽창해 저스트 창이 열렸을 때 검사한다. 현재 에디터의 `DA_Enemy_PureEntity_Ranged01`은 PureEntity·Ranged·반경 60cm이며 연결된 `DA_NPC_Pistol`은 속도 1000cm/s·피격 반경 5cm다. 이는 에셋 조회이며 개별 발사체의 런타임 공유 프래그먼트를 측정한 것은 아니다.
- 현재 로그의 호스트 대시는 `just=0.12`로 기록된다. 반경 확대는 공간 조건을 바꾸며 0.12초 창 자체를 늘리지 않는다. 사용자에게 공격 종류·수정 에셋·변경 전후 값·호스트/게스트·PIE 재시작 여부를 질문했고 원인은 아직 확정하지 않았다. 난도 수치나 사용자 에셋은 변경하지 않았다.
- 사용자 답변: NPC 산탄의 일부 회피·일부 피격을 배제하기 위해 각 적 DA의 `HexRingCount`를 1→0, `ParryRadius`를 15→60으로 바꿨다. 게스트 화면을 보며 호스트 캐릭터를 조작하고 있다. 에디터 조회로 순수 엔티티 Ranged01·Flyer01·Crawler01 세 에셋 모두 반경 60·링 0을 확인했다.
- 링 1→0은 발사당 7발→중앙 1발이다. 주변 탄 하나라도 저스트 창에 걸릴 기회가 줄어드는 효과와 반경 증가 효과가 함께 바뀌었으므로 난도 비교를 한 변수의 효과로 단정하지 않는다. 반경은 피격자 캡슐에 추가하는 값이므로 15→60은 전체 반경 4배가 아니라 45cm 확대다.
- 게스트의 Ghost·원격 대시는 수신 정보로 재구성되지만 호스트 입력의 판정은 서버에서 이루어지며 호스트는 원격 게스트용 피격 유예 대상이 아니다. 이 시각 차이가 체감 원인인지는 아직 확인하지 않았다. 현재 단발·반경 60을 유지하고 PktLag 0에서 호스트 본인 화면으로 성공 타이밍만 비교해 달라고 요청했다. 관통 재검증·난도 원인은 계속 미확인이다.

### 원격 플레이어 Ghost 착탄 CVar A/B 추가

- 사용자 비교 결과: 호스트 본인 화면에서도 성공 난도는 비슷했다. 사용자는 링 수 감소의 영향이라는 설명에 동의했다. 난도 회귀를 발견한 것으로 기록하지 않으며 사용자 반경·발사 수는 바꾸지 않았다.
- 원격 미러 뒤에도 PktLag 0에서 저스트 회피 성공의 체감상 약 절반은 Ghost가 통과하고 나머지는 소멸한다고 보고했다. 정확한 건수 집계나 탄별 소멸 원인 대조는 없다. PktLag 50 재검증 보고는 없다.
- 사용자가 복잡한 로직 대신 서버 판정 후처리를 CVar로 비교하기를 요청했다. `LNPProjectileProcessors.cpp` 한 파일에 `LNP.Projectile.PredictRemotePlayerImpact`(기본 1·Cheat)를 추가했다. 0이면 원격 플레이어만 클라이언트 코스메틱 충돌 후보에서 빼 기존 서버 착탄 큐로 정리한다. 1은 현재 예측·원격 무적 미러를 그대로 사용한다. Ghost 비행·적/로컬 플레이어·지형/수명·서버 판정·피해는 유지하며 보류/복구 큐는 없다.
- Live Coding 성공(UBT 18.63초, CPP 컴파일 1개). `SearchCVars`로 에디터 등록과 현재값 1을 확인했다. CVar 분기만 추가한 단위라 새 자동화 테스트는 만들지 않았으며 런타임 전환·체감은 사용자 A/B로 확인한다. 기존 42.82초 정규 빌드는 이번 CVar 추가 전 결과이고, 최종 정규 빌드는 아직 남아 있다.
- 사용자에게 단발·반경 60·미리보기 0·양쪽 PktLag 0에서 게스트 콘솔의 CVar 0/1을 비교하도록 요청했다. 회피 탄의 오소멸 감소와 일반 명중 탄의 늦은 소멸/관통 체감, 뒤 지형 착탄을 확인하고 CVar 1로 복원한다. 결과를 받은 뒤 기본 정책과 다음 단위 진행 여부를 확인한다.

### 서버 착탄 모드 미소멸 보고·진단

- 사용자는 값 0에서 Ghost가 조금 늦게 사라지는 정도가 아니라 아예 사라지지 않는 것 같다고 보고했다. 비교를 잠시 멈추고 1 복원을 요청했다. 일반 피격·저스트 회피 뒤·지형 착탄 중 어떤 경우인지 질문했으며 아직 답변 대기다.
- `GCN_LNP_Projectile_Impact`의 실제 부모와 CDO 태그는 정상이다. `GetCueInfo`는 작동이 확인된 성공 큐까지 notify 없음으로 반환해 그 조회만으로 큐 연결 누락을 판정하지 않았다.
- UE 5.8의 `PolymorphicNetSerializer.cpp`는 파생 컨텍스트 descriptor를 만들고, `ReplicationStateDescriptorBuilder.cpp`의 `DerivedFromCustom` 분기는 부모 전용 직렬화기 뒤에 리플렉션 필드만 추가한다. `FLNPProjectileImpactContext`의 키 3개에는 UPROPERTY가 없어 게스트에서 기본값이 될 가능성이 유력하다. 기존 `.context/TechDesign_Networking.md`의 GE 컨텍스트 NetSerialize 설명과 상충하므로 런타임 송수신 대조 후 정정한다.
- 기존 Dodge 디버그 옵션 아래 서버 Send와 수신 Receive 로그를 추가했다. 키·pellet index·컨텍스트 타입·net mode·Ghost 검색 성공을 기록한다. Live Coding 통과(UBT 71.61초). 사용자에게 로그 1·게스트 CVar 0에서 호스트가 대시 없이 탄 2~3발에 맞는 재현을 요청했다. 복구/보류 구조나 복제 필드 수정은 아직 하지 않았다.

### 식별자 전송 누락 확정·최소 수정

- 사용자는 일부러 회피하지 않고 맞았으며, 호스트 HP가 줄고 착탄 임팩트도 있었지만 탄이 화면 밖까지 계속 날았고 지면에 닿았을 때 소멸했다고 확인했다. 진단 로그 추가 뒤 일반 피격에서도 동일하게 재현했다.
- 로그 06:47:21~06:47:33 UTC 구간에서 클라이언트 Receive 10건 모두 key=0·destroyed=0이었다. 예: 서버 Send key=-213342·index=0 → 리슨 호스트 Receive net=2 key=-213342 → 게스트 Receive net=3 key=0. 컨텍스트 타입은 양쪽 모두 LNPProjectileImpactContext이며 VFX는 재생되므로, 큐 전달 자체가 아니라 파생 키 필드 전달 누락이다. 호스트 net=2에 Ghost가 없어 destroyed=0인 것은 정상이다.
- `FLNPProjectileImpactContext`의 PredictionKeyID·SpawnIndex·InstigatorPlayerID에 UPROPERTY를 추가했다. 엔진 descriptor builder의 DerivedFromCustom 동작과 일치시키는 수정 3곳이며, 레거시 NetSerialize·Ghost 키 계산·서버 판정은 유지했다. `.context/TechDesign_Networking.md`의 기존 예외 설명은 잘못됐으므로 실측 근거로 정정했다.
- 사용자가 저장 후 에디터 종료를 확인했고 프로세스 부재를 확인했다. 기존 Iris descriptor를 재사용하지 않도록 정규 `-DisableAdaptiveUnity` 빌드를 시작했다. 빌드 뒤 에디터 재실행·일반 명중의 키 일치/소멸부터 확인하고 A/B를 재개한다. 현재 정규 빌드·수정 후 런타임 결과는 대기 중이다.
- 정규 빌드 결과: UHT 포함 `LootNPopEditor Win64 Development -WaitMutex -NoHotReloadFromIDE -DisableAdaptiveUnity` 성공, 11개 작업·75.40초. 사용자에게 에디터 재실행·2인 PIE·양쪽 PktLag 0·로그 1·게스트 CVar 0에서 일반 명중 소멸을 먼저 확인하고, 정상이면 회피 관통·일반 명중 지연 체감을 비교하도록 요청했다. 종료 뒤 CVar 1 복원을 안내했다. 수정 후 런타임 검증은 아직 대기 중이다. 다른 작업의 문서와 사용자 에셋 변경이 있는 트리여서 깨끗한 트리 빌드로 기록하지 않는다.

### 수정 후 일반 명중 소멸 확인·잔여 성공 연출 질문

- 사용자는 일반 명중에서 탄이 잘 소멸하며 PktLag 0에서는 지연도 체감되지 않는다고 확인했다. 여전히 저스트 회피 이펙트와 함께 탄이 가끔 소멸하며, 이펙트의 오예측인지 질문했다.
- 새 로그에서 클라이언트 Receive 52건 중 key=0은 0건, destroyed=1은 33건이다. 정상 키와 실제 Ghost 검색 성공이 확인돼 기존 전송 누락 수정은 동작한다. destroyed=0 자체는 이미 로컬 소멸했거나 미스폰일 수도 있어 실패율로 해석하지 않는다.
- 서버 JustDodge success 19건·Retro JustDodged 0건이며 성공 큐는 서버 확정 경로다. 따라서 이번 보고를 연출 오예측 또는 소급 회피의 탄 소멸 예외라고 설명하지 않는다. 개별 성공 탄의 식별자를 성공 로그에 담지는 않아, 특정 시각의 소멸을 어느 성공과 같은 탄으로 묶어 확정할 근거는 부족하다.
- 에디터의 현재 미리보기 값은 0, 착탄 CVar는 1이며 새 로그에는 해당 CVar의 0 전환 기록이 없다. 테스트 후 복원했을 수 있으므로 당시 0을 확인했는지 사용자에게 질문했다. 기본 정책 결정·추가 소멸 원인 추적은 답변을 받은 뒤 진행한다. 코드는 추가 변경하지 않았다.
- 사용자가 1에서 테스트했다고 확인했다. 잔여 소멸은 기존 로컬 예측 모드의 결과로 기록하고, 서버 착탄 모드의 실패나 성공 이펙트 오예측으로 해석하지 않는다. 게스트 콘솔에서 CVar 0 출력 확인 후 같은 PktLag 0 조건으로 회피 관통·일반 명중 지연 체감을 재검증하도록 요청했다. 이번에는 결과 확인 때까지 0을 유지하도록 안내했다. 추가 코드 변경은 없다.

### 실제 값 0 A/B 통과 — 기본 정책 제안

- 사용자는 0을 입력한 뒤 PktLag 0에서 회피 성공 탄 소멸을 한 번도 보지 못했고, 일반 명중의 지연 소멸도 체감되지 않았다고 확인했다. 이어 호스트·게스트 양쪽 PktLag 50에서도 회피 관통을 확인했고, 탄 지연 소멸이 거의 느껴지지 않으며 어색함 없이 상당히 자연스럽다고 평가했다.
- 로그에서 07:08:05.476 UTC CVar 0 적용, 07:08:11.793 값 0 조회 확인, 07:12:14.230·07:12:17.959 양쪽 PktLag 50 입력을 확인했다. 에디터 현재값도 0이다. 비교 종료 후 지연 복원 여부는 아직 확인하지 않았다.
- CVar 0·지연 0 구간(적용부터 첫 PktLag 50 입력 전): 서버 성공 18건·클라이언트 착탄 수신 141건·Ghost 검색 소멸 성공 119건·키 0 누락 0건·소급 성공 0건. 양쪽 PktLag 50 입력 뒤 구간: 서버 성공 11건·수신 37건·검색 소멸 성공 34건·키 0 누락 0건·소급 성공 0건. 이 계수는 성공률·오소멸률 측정이 아니며, 관통의 자연스러움과 성공 탄 소멸 미관찰은 사용자 관찰 근거다.
- A/B 주요 검증을 마감하고 기본값 0 채택을 다음 작은 구현 단위로 권했다. 아직 소스 기본값 1은 변경하지 않았다. 원격 미러·임시 테스트 명령·진단 로그 제거 또는 그래픽스 다음 단위 진행까지 승인받은 것으로 확대하지 않는다. 다음 단위 진행 여부와 양쪽 PktLag 0 복원을 사용자에게 확인한다.

### 세션 마감 — CVar 보존·기본값 0만 반영

- 사용자가 양쪽 PktLag 50을 RTT 200ms로 이해했는지 질문했다. 엔진 FlushNet 송신 지연과 로그를 확인해 편도 각각 +50ms·추가 RTT 약 +100ms라고 설명했다. 실제 로그의 RTT는 설정 후 106~158ms이며 RTT 200ms 검증으로 기록하지 않는다.
- 사용자는 추가 정책 검토를 별도 작업으로 남기고 이번에는 CVar를 보존하면서 기본값만 0으로 바꿔 마감하도록 정했다(J-026). CVar 기본값과 영어 도움말을 수정했다. 원격 무적 미러·복제 오프셋·전용 테스트·임시 명령·진단 로그를 제거하지 않았으며 사용자 적 에셋도 수정하지 않았다.
- 기본값 변경 최종 정규 빌드: 컴파일 뒤 DLL이 UnrealEditor에 사용 중이라 링크 실패(70.81초). 사용자에게 저장·종료를 요청해 확인한 뒤 같은 `LootNPopEditor Win64 Development -WaitMutex -NoHotReloadFromIDE -DisableAdaptiveUnity`를 재실행했다. 남은 링크/메타데이터 2개 작업이 2.84초에 성공해 최종 빌드 통과. 컴파일 진단 오류가 아닌 파일 잠금이었다.
- 마지막 변경은 이미 A/B로 확인한 값 0을 기본값으로 설정하는 것과 도움말뿐이므로 같은 플레이 검증이나 기존 자동화 테스트를 반복하지 않았다. Current·Decisions·설계·검증 규약·실행서·로드맵을 실제 마감 상태로 갱신했다. 일반 명중/관통·지연 체감 외 미확인 경계는 통과로 확대하지 않았다. 새로운 구현 단위는 시작하지 않는다.

### 원격 플레이어 착탄 탄속 분기로 교체

- 사용자가 상용 방식 비교 뒤 소멸한 Ghost의 숨김·복구를 포함한 완전한 예측을 제외하고, 탄속 분기로 `PredictRemotePlayerImpact`를 교체하도록 정했다(J-027, J-026 대체).
- `LNPProjectileProcessors.cpp`에서 원격 플레이어를 항상 수집하고 `bRemotePlayer`로 표시한 뒤, 탄별 충돌 루프에서 `Proj.Velocity.Size() < LNP.Projectile.RemoteImpactPredictMinSpeed`이면 건너뛴다. 기본값은 3000 cm/s다. 값 0은 항상 예측, 충분히 큰 값은 항상 대기다.
- 에디터 에셋 조회 값은 `DA_Rifle`·`DA_Pistol` 5000 cm/s, `DA_Shotgun`·`DA_NPC_Pistol` 1000 cm/s다. 기본 팀에서 플레이어끼리는 맞지 않으므로 현재 PvE의 원격 플레이어 접촉은 NPC 1000 cm/s 탄이며 서버 착탄 대기를 유지한다.
- Live Coding 컴파일·링크는 성공했지만 신규 CVar는 `SearchCVars`에 나타나지 않았고, 기존 CVar만 남아 있었다. 정적 초기화가 돌지 않은 패치로 PIE를 켜면 클라이언트 분기의 CVar 조회가 안전하지 않으므로 이 세션에서는 PIE를 실행하지 않았다.
- 사용자 에디터 종료 뒤 프로세스 부재를 확인하고 정규 `LootNPopEditor Win64 Development -WaitMutex -NoHotReloadFromIDE -DisableAdaptiveUnity` 빌드를 통과했다(6개 작업·37.26초). 재시작한 에디터의 `SearchCVars`에서 신규 CVar 값 3000과 기존 CVar 제거를 확인했다. 다른 작업의 변경이 있는 트리이므로 깨끗한 트리 빌드로 기록하지 않는다.
- 사용자 2인 PIE 확인: 느린 NPC 탄에서 값 0은 저스트 회피 무적 판정에 성공해도 탄이 가끔 막혔고, 값 999999에서는 한 번도 보지 못했다. 일반 명중의 관통은 탄속이 느려 두 값 모두 체감하기 어려웠다. 의도대로 동작한다는 사용자 판단으로 기록한다. 건수를 집계하지는 않았고, 기준 이상의 실제 고속 탄으로 시험하지는 않았다.
