# Bastion_00 전체 단순화 재제작 — 새 세션 인계

> 2026-10-12 전체 단순화 재제작·장치 개편·발견된 나선 끼임 수정 완료. [V001 메시·외피](Phase09_BastionLowPolyV001.md), [V002 패널·훅](Phase09_BastionDevicesV002.md), [V003 나선 틈](Phase09_BastionSpiralGapV003.md)의 베이크·자동 검사·사용자 PIE 결과를 현재 기준으로 삼는다. 나선 양측 낙하도 사용자 확인을 통과했다. 아래의 미착수 설명은 실행 전 인계 시점의 기록이며 Phase 전체의 후속 Gate와 구분한다.

2026-10-11 사용자 요청. Hollow_00의 전체 단순화 결과를 Bastion_00에도 적용한다. **이번 세션은 문서와 인계만 갱신했다. Bastion 코드·메시·LVI·SurfaceData는 아직 변경하지 않았다.** 기존 Bastion 1차 채택본을 기준선으로 보존하고, 새 후보가 베이크·자동 검사·사용자 PIE를 통과한 뒤 교체를 확정한다.

## 1. 새 세션의 시작점과 작업 범위

1. 프로젝트 `AGENTS.md`·`CLAUDE.md`, [README](../README.md)·[Current](../Current.md)·[Decisions](../Decisions.md)를 읽는다.
2. 이 문서와 [공통 설계 가이드](../../Guide_OctantLevelDesign.md), [제작 가이드](../../Guide_OctantLevelInstance.md)를 읽는다.
3. 보존할 경험은 [Bastion 채택 기록](../history/Phase09_BastionGeometryNotes.md), 현재 생성 원본은 `Source/LootNPopEditor/SurfaceNavigation/LNPSliceOctant.cpp`의 `Bastion()`에서 확인한다. 옛 문서의 최초 8채 초안보다 현재 코드와 후기 사용자 채택 기록을 우선한다.
4. Hollow의 최종 근거는 [V017 외피](Phase09_HollowLowPolyV017.md)·[V020 훅](Phase09_HollowDevicesV020.md)이다. 실패 원인 조사가 필요할 때만 [V010](Phase09_HollowLowPolyV010.md)·[V016](Phase09_HollowLowPolyV016.md)을 추가로 읽는다.

목표는 단순한 폴리곤 수 감축과 함께 닫힌 충돌 외피, 읽기 쉬운 큰 덩어리, 안정적인 보행·훅 착지·복귀를 얻는 것이다. 기존 메시 전체에 일괄 Decimate를 적용하는 작업으로 해석하지 않는다. 경험과 연결 관계를 남기고 불필요한 내부 면·촘촘한 반복 분할·장식 밑동·국소 보정 부품을 줄인다.

이번 범위는 Bastion 제작이다. 승인 Hollow 외피·장치, Meadow 이음매, NPC LoS·이동 설정·베이커/내비게이션 알고리즘은 다른 작업 범위다. Phase 9의 풀 조합·패키지·부하 Gate도 별도 완료 조건으로 유지한다. 변경 중 드러난 제작 결함은 원본 형상과 배치부터 해결한다.

## 2. Hollow에서 실제로 효과가 있었던 방식

| 정리 방법 | 효과와 Bastion 적용 원칙 |
|:---|:---|
| 이어진 암반·경사·굴을 큰 닫힌 몸체로 다시 구성 | 작은 봉합 메시를 계속 늘리는 방식에서 벗어났다. Bastion도 성벽/층계참/건물/교량 접합의 실제 외피 소유자를 먼저 정한다 |
| 판·직육면체·쐐기·경로 단면에서 시작, 필요한 공간을 절삭 | 큰 이동·전투 공간을 간결하게 표현했다. 보행 가능한 윗면뿐 아니라 측벽·밑면·천장·문을 함께 설계한다 |
| 겹친 내부 면 제거 후 구면 투영·필요한 곳만 분할 | Boolean 또는 직접 토폴로지로 형상을 정리하고 곡률/법선/통행 오차에 따라 분할했다. 정교한 외형을 유지하기 위한 균일 고밀도 분할을 피한다 |
| 닫힌 원본 검증 후 Floor/Coarse/Shell 분리 | 바닥과 막는 외피의 역할을 명시했다. 열린 역할 조각에서 법선을 다시 계산하지 않고 원본 winding을 보존한다 |
| 지각·독립 섬·장치와 이어진 내부 외피의 소유권 분리 | Hollow는 지각/이음매·판형 섬4개·마커를 코드, 이어진 내부 외피를 Blender가 소유했다. Bastion에서는 구조에 맞게 다시 나눈다 |
| 작은 기존 치수보다 이동 경험·복귀 관계를 기준으로 재배치 | 전체 외피를 바꾼 뒤 앵커·Pod·출구도 다시 검사했다. 옛 좌표가 보존됐다는 이유만으로 새 배치가 검증된 것은 아니다 |
| 원본 → 반입 → 최종 조립 Chaos → 베이크 데이터 → 사용자 PIE 분리 | 각 단계에서 잡는 오류가 다르다. 앞 단계의 통과를 다음 단계의 완료로 확대하지 않는다 |

Hollow는 연결된 내부 외피가 한 성분이었다. **Bastion의 독립 공중섬까지 한 성분으로 합칠 필요는 없다.** 각 이어진 몸체의 폐쇄와 구역 접합을 확인한다. 원래 비어야 하는 심연·나선 틈·문·비행 전투 공간은 그대로 빈 공간이다.

## 3. Bastion에서 보존할 경험과 중점 구역

아래는 현 코드·채택 기록의 시작 기준이다. 실제 원본/에셋과 대조해 최신 수치를 기록한다. 폴리곤 단순화를 위해 세부 외형과 분할을 바꾸되, 연결을 없애거나 전투 공간을 좁히는 변경은 기능과 복귀를 다시 설계한다.

| 구역 | 보존할 역할 | 단순화 시 반드시 볼 부분 |
|:---|:---|:---|
| 정상 접시·나팔 | 고도180m·명목 반지름40m의 주 목적지 실루엣과 전투 공간 | 원주 분할을 줄여도 외곽 착지 폭·경사로 출구·엄폐/조망이 유지되는지. 나팔 밑면을 훅이 관통하지 않는지 |
| 중앙 기둥·나선 | 공동−100m부터 정상까지의 연속 보행과 지상/성채 다리 접속 | 기둥 반경10m·나선 틈2m·폭9m는 현재 spec 값이다. 틈을 Union/봉합으로 없애지 않는다. 안쪽/중앙/바깥 보행, 밑면→옆면→윗면의 벽보행 합류를 확인한다 |
| 성채·외성벽 | 다층 순환, 문을 통한 진입, 경사로 옆 보행 공간 | 환형 구조의 분할·경사 상단 층계참·문 모서리·지각 접합. 주 통로를 대각선 면이나 밑면이 가로막지 않는지 |
| 안뜰 건물·지붕 연결 | 비워 둔 북/남 전투 광장, 현재 남은 건물과 성벽/지붕 연결 | 제거했던 B01/B05와 머리 위 교량을 되살리지 않는다. 여섯 안뜰 건물의 지붕↔연결 발판↔다리 접합을 같은 좌표 변환으로 처리한다 |
| 전투 발판·공중섬·남쪽 빠른 상승 | Pod 전투 여유, 중간 착지, 정상 접근·하강 복귀 | T01~T03·I01/I06/I10의 넓은 전투장, V01~V04의 엇갈린 배치, 폐허 개구부와 다음 섬 밑면 가림 |
| 심연·공동·지하 발판 | 낙하 진입, 공동 전투, 나선과 두 훅 체인의 지상 복귀 | 지각 입구를 막지 않는 바닥/천장, C01~C06의 착지·연속 탈출, 문 위 앵커의 몸체 접근 |
| Pod·훅·패널 | 탐색·회피·연속 이동·복귀 | 모서리/천장 매몰, 다음 목표 식별, 관성 착지, 패널 전 경로·접안·주변 우회 거리 |

기록상 지정 Pod12개·NPC 편성125마리·훅135개다. 이 숫자는 작업 전 실제 코드/생성 로그와 대조할 스냅샷이며 현재 측정값을 대신하지 않는다. Pod별 편성은 원본을 보존한다. 훅은 목적별 목록을 만든 뒤 중복 역할을 통합할 수 있지만, Hollow의 훅25개나 잔도당1개 규칙을 Bastion 전체에 기계적으로 적용하지 않는다. 반대쪽 회피·지붕 연결·하층 탈출처럼 다른 기능을 가진 훅은 기능으로 판단한다.

### 제작 소유권 제안 — 착수 시 확정

- 지각·300m 반지름·이음매 보존/전이 띠는 기존 코드 경로를 유지한다. Bastion 현재 `SeamBand=2000cm`, 보존15m이며 실행 전 spec을 다시 읽는다.
- 규칙적인 환형 벽·단순 섬·나선은 기존 코드의 분할과 실제 외피를 정리하는 방법부터 비교한다. 기존 생성기가 간단하고 안전하면 유지한다.
- 서로 물리는 건물/다리/경사·공동의 복잡한 접합은 구역 단위의 닫힌 Blender 외피 또는 공유 단면으로 정리한다. 옥탄트 전체를 무조건 Boolean Union하는 접근은 피한다.
- 각 구역의 새 원본, 대체할 Generated part ID/기존 Authored, 공유 경계, 유지할 Pod/마커를 표로 확정한다. 승인 Authored를 배치할 때 겹치는 기존 생성 경로도 함께 교체한다.
- 전역 `DishSides`·나선 분할·공통 생성 함수 변경은 Hollow나 다른 옥탄트에 영향을 줄 수 있다. Bastion에 필요한 변경만 적용하고 공통 변경이 필요하면 영향 검사를 명시한다.

## 4. 새 세션 실행 순서와 통과 조건

### 1) 기준선과 복구

`git status`로 다른 세션 변경을 확인하고 관련 파일/에셋만 저장한다. Bastion 코드 spec·Blender 원본(있으면)·Authored/Generated·지각·LVI·SurfaceData·마커 transform/개별 사거리를 버전 복구본에 남긴다. 현재 에디터 수동 배치가 있다면 생성 전 원본과 차이를 먼저 반영한다.

작업 전 표: 지각/Generated/Authored별 삼각형·합계, 실제 충돌 LOD/complex mesh/profile, Support/Layers/샘플/payload, Nav cells/components/portals/후보/시간/payload, Spawn 후보/편성, seam, 기존 경고와 실패. 현재 베이크와 자동 검사 결과를 수집해 새로 생긴 문제를 구분한다. 이번 문서 작성에서는 Bastion 기준선 측정·생성·베이크를 실행하지 않았다.

### 2) 큰 형상과 대표 접합

평면·단면·연결표와 교체 목록을 만든다. 지붕↔다리↔성벽 접합, 나선↔지상/정상 접속, 공동 탈출 같은 위험 구역을 원본에서 먼저 확인한다. 기존의 검증된 FBX/역할/좌표 절차를 재사용하며 새 도구나 전용 자동화 장치부터 만들지 않는다. 원본의 큰 덩어리와 cutter를 남기고 내부 면을 제거한 뒤 투영한다.

### 3) 원본과 반입 검사

- 각 몸체의 비다양체·면 방향·퇴화·중복·예상 밖 경계·교차를 검사한다. 열린 문은 두께 있는 개구부이며 구멍 난 외피와 구별한다. 자기교차 검사의 제외 조건도 기록한다.
- 최종 구면에서 경로 전체 폭·양 가장자리·굽이·문/천장·접합을 검사한다. 큰 삼각형은 현 오차와 예상/실제 법선 오차를 함께 본다. 필요한 공유 변만 추가 분할한다.
- 닫힌 원본을 Floor/Coarse/Shell로 나눠 면 수 합계·공유 경계·모든 면의 winding 보존을 검사한다. Support 역할 출력 정점의 UE 각 축 int16 표현 범위도 확인한다.
- FBX·manifest·편집 원본을 버전별 저장한다. 스크립트 재생성 원본은 `Scripts/Blender/`, 수작업 유일 원본은 `Art/Octants/Bastion_00/`에 보존하고 Saved만 원본으로 두지 않는다.
- staging 예: `/Game/Maps/_WorkInProgress/OctantWorkflow/BastionLowPolyV001`(Git 제외). triangle/bounds·단면 충돌 방향·LOD0/별도 complex 유무·complex-as-simple·역할 profile을 실제 반입 에셋에서 재조회한다. production은 통과한 명시 버전만 선택하고 이전 버전의 중복 배치를 막는다.

`GenerateSliceOctant.py`의 현재 `MESAS["Bastion_00"]`는 비어 있다. 이 파일만 실행하면 Bastion 전체가 만들어지는 것이 아니다. Hollow의 `BuildHollowLowPoly.py`는 좌표/투영/분할/역할 출력의 참고 구현이며, Hollow 경로·경계·cutter를 Bastion에 그대로 실행하지 않는다.

### 4) 실제 조립 → 생성·베이크 → 자동 검사

코드 변경이 있으면 Live Coding 성공을 먼저 확인한다. PIE를 종료한 상태에서 다음 명령을 한 묶음으로 실행하고 오류 시 다음 명령을 멈춘다.

```text
LNP.SurfaceNav.LintSliceOctant Bastion_00
LNP.SurfaceNav.BuildSliceOctant Bastion_00
LNP.SurfaceNav.BakeOctant /Game/Maps/Bastion_00/LVI_Octant_Bastion_00
```

콘솔 실행 방법은 제작 가이드 §6과 당시 사용 가능한 도구를 확인한다. 현재는 프로젝트 콘솔 실행 API가 없어 사용자에게 이 조작만 요청한다. 생성은 기존 LVI 액터를 지우고 spec으로 다시 배치하므로 수동 수정본을 먼저 보존한다. 같은 오류로 재베이크를 반복하기 전에 원본/최종 조립에서 원인을 해결한다.

기존 `LootNPop.SurfaceNavigation.Bake.BastionEncounters`, `LootNPop.SurfaceNavigation.Runtime.ProductionSurfaceDataDefinitions`를 실행한다. 전자는 Pod 편성/출현 후보 검사이므로 보행·외피·훅 착지를 증명하지 않는다. 필요한 실제 지형 검사는 Hollow의 격리 Chaos 검사 방식을 참고해 기존 진단에 추가하되, Hollow 전용 좌표나 테스트 통과를 Bastion의 증거로 사용하지 않는다.

자동 검사의 목표:

- 나선 안/중앙/바깥, 환형 통로·지붕 연결·교량·지각 경계의 바닥과 플레이어 캡슐을 **양방향** 검사. 천장·측면·접합 모서리도 포함한다.
- 원래 걷는 연결의 실제 Nav 왕복과 의도한 정적 보행 단절, 8slot 회전의 투영·Pod 머리 공간/가장자리·기존 편성과 seed별 후보를 검사한다.
- 모든 훅의 역할·대표 출발점·개별 사거리·시야·몸체 접근·의도한 첫 착지면·종료 관성 낙하를 검사한다. `GrappleMaxDistance=0`인 Bastion 마커는 공통 config를 쓰므로 런타임 `GetMaxGrappleDistance()`와 같은 유효 사거리로 검사한다. 0을 사거리0cm로 비교하는 Hollow 전용 검사 복사를 피한다. 수직 축처럼 바로 아래 바닥이 없는 훅은 별도 역할로 다룬다.
- 패널을 유지/조정했다면 전체 경로의 중앙/가장자리/모서리와 양 끝 접안, 현지 중력 수평 자세를 검사한다. Hollow의12×12m 크기는 채택된 사례이며 Bastion의 장치 변경 요구를 대신하지 않는다.
- lint/반입/베이크/검사의 오류·경고와 비용 표를 남긴다. 경고를 없애려고 통행·편성·좌표 상한의 기준부터 낮추지 않는다.

### 5) 마지막 사용자 PIE를 한 묶음으로 요청

베이크·자동 검사와 제작자 외형/충돌 확인이 끝난 뒤 TestMap03 서버 PIE에서 검토한다. 시작 시 `LNP.Debug.TeleportToReview`로 실제 Bastion slot·검토점 목록을 확인한다. 확인된 이름에 `LNP.Debug.TeleportToReview <Name> <Slot>`을 쓴다.

1. `NorthGate`에서 자연 진입 → 안뜰 → 성벽/성채 경사·문 → 지붕 다리의 양방향 보행. 가장자리 걸림·조망·빈 전투 광장을 확인한다.
2. `Cavern`에서 나선으로 지상/정상까지 걷고, 두 지하 훅 체인으로 별도 탈출·하강/중도 해제·추락 복귀를 확인한다.
3. `PodTerraceNorth/South/Citadel`, `SkyRuinLow/High`, `FastAscentBase/Top`의 전투 공간·연속 훅 착지·정상 접시 도달을 확인한다.
4. 패널 호스트/게스트 탑승·접안·회전과 인접 가장자리의 우회, 넉백 중 사용 공간·추락 후 복귀를 확인한다.
5. 적을 켠 Pod 사수/회피/복귀와 벽보행 합류·비행 접근을 확인한다. 별도 NPC LoS 결함은 지형 제작 실패와 구분해 기록한다.

문제는 `LNP.Debug.WhereAmI`의 slot/local X/Y/H·발밑 메시와 사용한 훅/이동 방향으로 받는다. 당시 접시/문/계단의 숫자나 중심 광선 통과보다 실제 플레이 결과를 우선한다. 초기 전체 검토 후 추가 수정은 영향 구간을 다시 자동 검사한 뒤 변경 구간 PIE로 묶는다.

## 5. Hollow의 실패에서 반드시 가져갈 점

| 놓친 점 | 다음 세션의 예방/검증 |
|:---|:---|
| V003 공동 Support 정점이 int16 좌표 상한을 초과 | 깊이뿐 아니라 투영 후 UE X/Y/Z 범위를 전체 Support 정점에서 검사. 좌표 인코딩을 넓히는 대신 공간/배치 조정 |
| V009 열린 역할 조각의 법선 재계산으로 바닥 방향 뒤집힘 | 닫힌 원본에서 검증한 winding을 분리·FBX·반입까지 보존 |
| V010 통로 캡슐은 통과했지만 Nav/접합/탈출구/Pod 머리 공간에서270오류 | 실제 소유 경계 전체·Nav 연결·출구 cutter 상한·비행형 요구 headroom을 별도 검사. 한 테스트 통과로 전체 완료 선언 금지 |

| Support 높이 띠 경계가 정상/좁은 입구를 끊음 | 주 착지 높이/연결을 가로지르는 역할 분할을 피하고, 좁은 접합에는 충분한 해상도를 유지. Coarse로 일괄 변경하지 않음 |
| 지형 검사 통과 뒤 상부 발판/천장이 앵커와 중간 판을 가림 | 최종 조립의 실제 마커에서 시야·캡슐 접근·출구 빈 공간 검사 |
| V018 접근선 통과에도 잔도에 못 착지하고 시드 훅까지 섞임 | 착지 역할과 첫 바닥/몸체 경로 확인. 수동 설계 영역의 추가 시드 정책을 해당 옥탄트에 명시적으로 정함 |
| V019 방사 광선·±60cm 바닥 통과 후 관성으로 잔도 이탈 | 실제 BP 정지 거리·종료 속도·중력·감속을 읽어 대표 시작점/주변과 여러 방향의 낙하를 검사 |
| V020 근사547사례 통과 후 실제 Chaos652사례 중 WestMid5방향 실패 | 근사 접근 판정이 실제 Chaos보다 많은 방향을 제외할 수 있음. 최종 판정은 Chaos로 하고 임시 후보 통과와 저장 LVI 통과를 구분 |

Hollow V020에서는 WestMid를 낮추고 안쪽으로 옮겨 저장 조립643관성낙하를 통과한 뒤 사용자 PIE도 통과했다. 관성 검사는 BP의 정지150cm·종료600cm/s·중력2000·측방 감속200·종단2000을 이용한60Hz 예측이었다. 다음 세션은 실제 설정을 다시 읽고, 이 예측을 실제 Mover/입력/착지감의 완전한 시뮬레이션으로 설명하지 않는다. Hollow의 바닥 반경400cm·대표 출발점 도착 여유100cm도 전역 규격이 아니라 해당 공간의 검사 범위다.

## 6. 인계·완료 증거

- 원본/스크립트·버전·FBX·manifest·UE 경로·복구 위치, 교체 목록과 실제 배치 버전을 기록한다.
- 기준선과 새 후보의 비용을 같은 표로 비교한다. 전체 감소율과 줄지 않은 메모리·샘플·Nav 비용을 함께 남긴다.
- 자동 검사의 대상/방향/제외 조건·실패 수정·최종 저장 조립 결과, 사용자 PIE에서 채택한 범위를 기록한다.
- 에디터에서 훅을 직접 조정했다면 **LVI 저장 → Bake → PIE**로 확인하고, 다음 Build 전에 위치/사거리를 코드 spec에 되돌려 반영한다. 월드 XYZ와 spec X/Y/H는 다른 좌표다. 이름 있는 역할로 관리하고 위치 변경에 맞춰 검사 기대 착지점도 갱신한다.
- Hollow V017 외피와 V019~V020 장치의 에셋 해시/설정을 작업 전후 비교해 승인본 보존을 확인한다. 다른 세션 dirty 변경을 되돌리거나 사용자 요청 없이 commit하지 않는다.
- 공통 형상/장치 생성 경로를 수정했다면 기존 `LootNPop.SurfaceNavigation.Bake.HollowContent` 등 영향받는 회귀 검사도 실행한다. 새 Bastion 검사 통과만으로 승인 Hollow 보존을 증명하지 않는다.

**다음 세션의 첫 구체적 작업:** Bastion 현재 생성 원본·에셋·수동 마커를 확인/백업하고 비용 기준선을 채운 뒤, 나선/정상·성벽/성채·건물/교량·공동/섬의 소유권과 교체 목록을 정한다. 그다음 대표 접합을 검증하며 전체 단순화 후보를 제작한다. 마지막 PIE까지 통과해야 Bastion 새 단순화 버전을 완료로 기록한다.
